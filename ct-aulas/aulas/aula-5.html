Na Aula 04 a Loja rodou num cluster kind, e você operava tudo: control plane, nós e add-ons.     5.1

    Do kind ao EKS: Kubernetes não gerenciado × gerenciado

    Conceito
    Capítulo 1 · A Loja vai para a nuvem

    Quem vai cuidar do etcd às 3h da manhã?

    Na Aula 04, o cluster kind cabia num codespace e você via cada peça: etcd, API server, scheduler. Em produção, alguém precisa manter essas peças em três zonas, fazer backup, aplicar patches e atualizar a versão três vezes por ano. A Loja decide entregar esse trabalho à AWS.

    EKS control plane × Kubernetes control plane

    Workflow de criação de um cluster EKS

    Ferramentas: AWS Management Console, AWS CloudFormation, Terraform (EKS Blueprints), AWS CLI e eksctl. Hoje: eksctl, com o cluster descrito num arquivo YAML.

    Referências: Get started with Amazon EKS · eksctl.io.

    eksctl: o cluster como um arquivo

    cluster.yaml
    apiVersion: eksctl.io/v1alpha5
kind: ClusterConfig
metadata:
  name: aula5
  region: us-east-1
  version: "1.37"
iam:
  serviceRoleARN: arn:aws:iam::123456789012:role/LabRole
vpc:
  subnets:
    public:
      us-east-1a: { id: subnet-0aaa… }
      us-east-1b: { id: subnet-0bbb… }
      us-east-1c: { id: subnet-0ccc… }
managedNodeGroups:
  - name: ng-loja
    instanceType: t3.medium
    minSize: 2
    desiredCapacity: 2
    maxSize: 3
    iam:
      instanceRoleARN: arn:aws:iam::123456789012:role/LabRole
addons:
  - name: vpc-cni
  - name: coredns
  - name: kube-proxy
  - name: eks-pod-identity-agent
  - name: metrics-server
    • CLI oficial do EKS: lê o ClusterConfig e cria tudo por CloudFormation (uma pilha para o cluster, uma por node group).
    • iam: no Learner Lab não dá para criar roles, então o cluster e os nós usam a LabRole pronta.
    • vpc.subnets: usa as sub-redes da VPC padrão em três zonas, sem criar NAT gateway.
    • addons: rede dos Pods (VPC CNI), DNS, kube-proxy, Pod Identity e metrics-server, como EKS add-ons.
    • version: sem ele, o eksctl v0.231.0 usaria a 1.34; fixamos a 1.37, a mais nova do EKS (a mesma do kind na Aula 04).
    • No fim, grava o contexto no seu ~/.kube/config.

    Referências: eksctl · Creating and managing clusters · VPC configuration · Addons · eksctl v0.231.0.

    Exercício 5.1.1

    Criando o cluster EKS com eksctl no Learner Lab

    ~15 min + 20 min de espera

    Preparar o codespace com as credenciais do Learner Lab, instalar AWS CLI e eksctl, descrever o cluster aula5 em YAML e disparar a criação.

    AWS Academy Learner Lab

    Use um codespace novo e uma sessão nova do lab. As permissões de IAM são limitadas: o cluster e os nós usam a role pronta LabRole. Trabalhe em us-east-1. A criação leva de 15 a 20 minutos; deixe o comando rodando num terminal e siga com a aula.

    1. No AWS Academy, abra o Learner Lab e clique em Start Lab. Aguarde a bolinha ao lado de AWS ficar verde.

      Clique em ⓘ AWS Details e, em AWS CLI, clique em Show. Copie o bloco abaixo, troque cada COLE_AQUI pelo valor correspondente e cole no terminal:

      terminal
      mkdir -p ~/.aws
cat > ~/.aws/credentials <<'EOF'
[default]
aws_access_key_id=COLE_AQUI
aws_secret_access_key=COLE_AQUI
aws_session_token=COLE_AQUI
EOF
printf '[default]\nregion = us-east-1\n' > ~/.aws/config
export AWS_REGION=us-east-1
      Credenciais temporárias

      Elas expiram quando a sessão do lab termina (cerca de 4 horas). Ao reiniciar o lab, repita este passo com os valores novos. Não publique essas chaves em repositório, chat ou print.

    2. Instale a AWS CLI v2:

      terminal
      curl -s "https://awscli.amazonaws.com/awscli-exe-linux-x86_64.zip" -o awscliv2.zip && unzip -q awscliv2.zip && sudo ./aws/install && rm -rf aws awscliv2.zip

      Valide as credenciais:

      terminal
      aws sts get-caller-identity --no-cli-pager

      Instale o eksctl v0.231.0:

      terminal
      curl -sL "https://github.com/eksctl-io/eksctl/releases/download/v0.231.0/eksctl_Linux_amd64.tar.gz" | tar -xz -C /tmp && sudo install -m 0755 /tmp/eksctl /usr/local/bin/eksctl && rm /tmp/eksctl

      Confira o eksctl e o kubectl:

      terminal
      eksctl version; kubectl version --client

    3. Crie a pasta da aula e descubra o ARN da LabRole e a VPC padrão:

      terminal
      mkdir -p ~/eks/aula-5 && cd ~/eks/aula-5
LAB_ROLE=$(aws iam get-role --role-name LabRole --query Role.Arn --output text)
VPC_ID=$(aws ec2 describe-vpcs --filters Name=isDefault,Values=true --query 'Vpcs[0].VpcId' --output text)
echo "$LAB_ROLE  $VPC_ID"

      Pegue as sub-redes da VPC padrão em us-east-1a, us-east-1b e us-east-1c:

      terminal
      subnet() { aws ec2 describe-subnets --filters Name=vpc-id,Values=$VPC_ID Name=availability-zone,Values=$1 --query 'Subnets[0].SubnetId' --output text; }
SUBNET_A=$(subnet us-east-1a); SUBNET_B=$(subnet us-east-1b); SUBNET_C=$(subnet us-east-1c)
echo "$SUBNET_A $SUBNET_B $SUBNET_C"

    4. Descreva o cluster. O heredoc sem aspas troca as variáveis pelos valores da sua conta:

      terminal
      cat > cluster.yaml <<EOF
apiVersion: eksctl.io/v1alpha5
kind: ClusterConfig
metadata:
  name: aula5
  region: us-east-1
  version: "1.37"
iam:
  serviceRoleARN: $LAB_ROLE
vpc:
  subnets:
    public:
      us-east-1a: { id: $SUBNET_A }
      us-east-1b: { id: $SUBNET_B }
      us-east-1c: { id: $SUBNET_C }
managedNodeGroups:
  - name: ng-loja
    instanceType: t3.medium
    minSize: 2
    desiredCapacity: 2
    maxSize: 3
    labels: { role: app }
    iam:
      instanceRoleARN: $LAB_ROLE
addons:
  - name: vpc-cni
  - name: coredns
  - name: kube-proxy
  - name: eks-pod-identity-agent
  - name: metrics-server
cloudWatch:
  clusterLogging:
    enableTypes: ["api", "audit", "authenticator", "controllerManager", "scheduler"]
EOF
cat cluster.yaml

      Veja o que o eksctl vai criar, sem criar nada:

      terminal
      eksctl create cluster -f cluster.yaml --dry-run | head -40

    5. Crie o cluster. Deixe rodando e siga com a aula (15 a 20 minutos):

      terminal
      eksctl create cluster -f cluster.yaml

      Em outro terminal, acompanhe as pilhas do CloudFormation que o eksctl criou:

      terminal
      aws cloudformation list-stacks --stack-status-filter CREATE_IN_PROGRESS CREATE_COMPLETE --query 'StackSummaries[?contains(StackName,`aula5`)].[StackName,StackStatus]' --output table
    Resultado esperado
    • aws sts get-caller-identity mostra a conta do lab e o ARN da role assumida (assumed-role/…); eksctl version responde 0.231.0.
    • O cluster.yaml sai com o ARN real da LabRole e três subnet-… diferentes.
    • Aparecem as pilhas eksctl-aula5-cluster e, depois, eksctl-aula5-nodegroup-ng-loja.
    • O eksctl create cluster termina com a mensagem de que o cluster aula5 está pronto e grava o contexto no kubeconfig.
    O que aprendemos com este exercício?
    • No EKS, criar o control plane é uma chamada de API: ninguém instala etcd nem API server.
    • O eksctl transforma um ClusterConfig em pilhas do CloudFormation: o cluster vira código versionável.
    • Cluster, add-ons e node groups são etapas separadas do workflow, mesmo quando um comando faz todas.
    • Em contas com IAM restrito, como o Learner Lab, roles prontas entram no lugar das que o eksctl criaria.
    Se a criação falhar

    Leia a mensagem do eksctl e os eventos da pilha no console do CloudFormation. Antes de tentar de novo, apague o que ficou pela metade com eksctl delete cluster -f cluster.yaml --wait.

    5.2

    O control plane do EKS

    Conceito
    Capítulo 2 · O cérebro que você não vê

    Onde foram parar o etcd e o API server?

    Enquanto o cluster sobe, a equipe procura os Pods do control plane, como fazia no kind. Eles não estão lá: no EKS, o control plane roda numa conta da AWS, numa VPC gerenciada pelo EKS, e só aparece para você como um endpoint.

    Arquitetura do control plane do EKS

    • Cada cluster tem o seu próprio control plane, sem nada compartilhado entre clusters ou contas.
    • Pelo menos 2 instâncias de API server e 3 de etcd, em 3 zonas de disponibilidade da região.
    • O etcd fica separado do API server, para operações e atualizações seguras e contínuas.
    • O endpoint é exposto por um NLB, e o EKS troca instâncias com problema, inclusive em outra zona.

    Referência: Amazon EKS architecture.

    O que a AWS garante no control plane

    Disponibilidade

    • Sobrevive à perda de uma zona inteira.
    • SLA de 99,95% mensal no endpoint da API (control plane padrão).
    • Instâncias com problema são substituídas automaticamente.

    Operação

    • Patches, backup e quórum do etcd são da AWS.
    • Ajuste automático de tamanho das instâncias do control plane.
    • Logs do control plane (API, audit, authenticator, controller manager, scheduler) opcionais no CloudWatch.

    Versões

    • Cada minor tem 14 meses de suporte padrão e mais 12 de suporte estendido, pago à parte.
    • Hoje, no padrão: 1.37, 1.36, 1.35 e 1.34.
    • Upgrade in-place pode voltar à minor anterior em até 7 dias.

    Referências: Amazon EKS SLA · Kubernetes version lifecycle on EKS · Control plane logs.

    Como os nós e o kubectl chegam ao control plane

    • O EKS cria de 2 a 4 interfaces de rede (ENIs) nas sub-redes do seu cluster. Por elas passa o tráfego entre control plane e nós, e também logs, exec, attach e port-forward.
    • O endpoint da API é público por padrão, protegido por IAM e RBAC. Dá para ligar o acesso privado (só de dentro da VPC) e limitar ou desligar o público.
    • Com o endpoint privado, o nome do cluster resolve para IPs da sua VPC (zona hospedada privada).

    Referências: VPC and subnet requirements · Cluster API server endpoint.

    • Para os Pods chamarem serviços da AWS: EKS Pod Identity (add-on eks-pod-identity-agent) ou IRSA.

    Referências: Access entries · Connect kubectl to an EKS cluster · EKS Pod Identity.

    O que aprendemos com este exercício?

    • A ponte entre o control plane e a sua VPC são ENIs gerenciadas pelo EKS.
    • O acesso ao cluster passa pelo IAM (token) e pelos access entries, antes do RBAC.
    • Rede dos Pods, DNS e kube-proxy viram EKS add-ons, com versão gerenciada pela API do EKS.

    Self-managed × managed node groups

    Self-managed nodes

    • Instâncias EC2 e Auto Scaling group seus, registrados no cluster.
    • Você escolhe e atualiza a AMI, o kubelet e o runtime.
    • Para AMI customizada, bootstrap especial ou requisitos que os outros modos não atendem.
    • Mais flexível, mais trabalho.

    Managed node groups

    • O EKS cria e gerencia o ASG na sua conta, nas zonas que você escolher.
    • Criar, atualizar ou encerrar nós é uma operação, e o EKS drena os nós antes.
    • AMI otimizada do EKS; o console avisa quando há atualização.
    • Sem custo extra: você paga só EC2, EBS e o cluster. É o que usamos no lab.

    Referências: Managed node groups · Self-managed nodes.

    Fargate × Auto Mode

    AWS Fargate

    • Sem servidores para escolher ou escalar: cada Pod roda isolado na própria VM.
    • Um Fargate profile diz quais Pods (namespace e labels) vão para o Fargate.
    • Não roda DaemonSets, hostNetwork, hostPort nem GPU; só sub-redes privadas.
    • Paga por Pod, pela CPU e memória pedidas.

    EKS Auto Mode

    • A AWS escolhe, cria, atualiza e encerra os nós (Karpenter por baixo), conforme os Pods pendentes.
    • AMIs Bottlerocket imutáveis, sem SSH; cada nó vive no máximo 21 dias.
    • Rede, load balancer, DNS e storage em bloco viram capacidades gerenciadas do cluster.
    • Paga uma taxa por instância além do EC2.

    Paralelo com a Aula 03: Fargate no EKS lembra o Fargate do ECS; Auto Mode lembra as ECS Managed Instances.

    Referências: AWS Fargate · EKS Auto Mode · Amazon EKS pricing.

    Quando usar cada uma

    OpçãoEscolha quandoEvite quando
    Managed node groupsPadrão para a maioria; controle das instâncias sem operar o ciclo de vidaPrecisa de bootstrap muito customizado
    Self-managedAMI própria, requisitos de compliance, OutpostsO time não tem tempo para patches e upgrades de nós
    FargatePoucos Pods, isolamento forte, cargas esporádicasDaemonSets (agentes de log e métricas), GPU, muitos Pods pequenos
    Auto ModeQuer o mínimo de operação de cluster e nósPrecisa de SSH no nó, AMI ou CNI customizados

    Referência: Compare compute options.

    Escalando os nós: Cluster Autoscaler e Karpenter

    • O HPA da Aula 04 cria mais Pods; se não houver espaço, eles ficam Pending.
    • O Cluster Autoscaler (CAS) vê os Pods pendentes e aumenta o Auto Scaling group; com nós ociosos, diminui.
    • O Karpenter cria direto a instância que cabe nos Pods pendentes (tipo, tamanho, spot ou on-demand) e consolida nós subutilizados.
    • No Auto Mode, o Karpenter já vem gerenciado pela AWS.

    Referências: Karpenter and Cluster Autoscaler · karpenter.sh v1.15.

    A rede dos Pods no EKS: VPC CNI

    • No kind, os Pods tinham IPs de uma rede interna (10.244.x.x, kindnet). No EKS, o add-on Amazon VPC CNI (Pods aws-node) dá a cada Pod um IP da própria VPC.
    • Os Pods falam direto com outros serviços da VPC (RDS, outros clusters) sem tradução de endereço.
    • Consequência: o número de Pods por nó depende de quantos IPs a instância comporta, e as sub-redes precisam de IPs livres.

    Referência: Amazon VPC CNI.

    Exercício 5.3.1

    Explorando e escalando o managed node group

    ~15 min

    Ver o que o EKS registrou nos nós do managed node group, confirmar que os Pods recebem IPs da VPC e adicionar um nó com um único comando.

    Antes de começar

    Usa o cluster aula5 do exercício 5.1.1. Trabalhe em ~/eks/aula-5.

    1. Veja o node group pelo eksctl:

      terminal
      eksctl get nodegroup --cluster aula5

      Veja os nós com os labels que o EKS e você colocaram:

      terminal
      kubectl get nodes -L eks.amazonaws.com/nodegroup,eks.amazonaws.com/capacityType,node.kubernetes.io/instance-type,topology.kubernetes.io/zone,role

      E o que roda por baixo de cada nó (SO, kubelet, runtime):

      terminal
      kubectl get nodes -o custom-columns=NODE:.metadata.name,OS:.status.nodeInfo.osImage,KUBELET:.status.nodeInfo.kubeletVersion,RUNTIME:.status.nodeInfo.containerRuntimeVersion

    2. Compare os IPs dos nós e dos Pods do kube-system:

      terminal
      kubectl get nodes -o wide | awk '{print $1, $6}'; kubectl get pods -n kube-system -o wide | awk '{print $1, $6, $7}'

      Confirme na AWS que esses IPs são da VPC padrão:

      terminal
      aws ec2 describe-vpcs --filters Name=isDefault,Values=true --query 'Vpcs[0].CidrBlock' --output text

    3. Veja o Auto Scaling group que o EKS criou para o node group:

      terminal
      aws eks describe-nodegroup --cluster-name aula5 --nodegroup-name ng-loja --query 'nodegroup.{status:status,ami:amiType,escala:scalingConfig,asg:resources.autoScalingGroups[0].name}' --output json

      Aumente o node group para 3 nós:

      terminal
      eksctl scale nodegroup --cluster aula5 --name ng-loja --nodes 3

      Acompanhe o nó novo entrar no cluster (2 a 4 minutos, Ctrl+C sai):

      terminal
      kubectl get nodes -L topology.kubernetes.io/zone -w

      Volte para 2 nós e veja um deles ser drenado e sair:

      terminal
      eksctl scale nodegroup --cluster aula5 --name ng-loja --nodes 2 && kubectl get nodes -w
    Resultado esperado
    • O node group ng-loja aparece com MIN 2, MAX 3, DESIRED 2 e instâncias t3.medium.
    • Os nós têm eks.amazonaws.com/nodegroup=ng-loja, capacityType=ON_DEMAND, role=app e zonas diferentes; o kubelet está na v1.37 e o runtime é o containerd.
    • Os IPs dos nós e dos Pods do kube-system estão dentro do CIDR da VPC padrão (por exemplo, 172.31.0.0/16).
    • O describe-nodegroup mostra o ASG eks-ng-loja-…; um terceiro nó fica Ready depois do scale e é removido ao voltar para 2 (passa por SchedulingDisabled antes de sair).
    O que aprendemos com este exercício?
    • Num managed node group, o EKS cria e opera o Auto Scaling group na sua conta: escalar é um comando.
    • Ao remover um nó, o EKS drena antes, respeitando os PDBs que você viu na Aula 04.
    • Com o VPC CNI, cada Pod recebe um IP da VPC, diferente da rede interna do kind.
    • Os labels de nó (zona, tipo, node group) são a base para espalhar e posicionar workloads.
    5.4

    A Loja no EKS: deploy, Service e operação

    Conceito
    Capítulo 4 · Os mesmos manifestos, outra nuvem

    O YAML da Aula 04 roda aqui?

    Chegou a hora das duas últimas etapas do workflow: implantar o workload e expor o serviço. A Loja reaproveita o que aprendeu no kind: namespace, Deployment, Service, rollout e rollback. O que muda é quem atende o type: LoadBalancer: agora é um load balancer de verdade da AWS.

    Service LoadBalancer no EKS

    • Sem nenhum controller extra, o controller de load balancer do provedor AWS, embutido no control plane do EKS, cria um Classic Load Balancer para cada Service LoadBalancer.
    • É o Service controller do cloud-controller-manager da Aula 04, agora com uma nuvem de verdade por trás (no kind, era o cloud-provider-kind).
    • Esse controller só recebe correções críticas. A AWS recomenda o AWS Load Balancer Controller, que cria NLB para Services e ALB para Ingress e Gateway API.

    Referências: Route TCP and UDP traffic with Network Load Balancers · AWS Load Balancer Controller.

    O que é igual e o que muda em relação ao kind

    kind (Aula 04)EKS (hoje)
    ManifestosOs mesmos: apps/v1, v1, probes, HPA, PDB
    kubectlOs mesmos comandos: apply, rollout, scale, logs, debug

    IPs dos PodsRede interna (kindnet)IPs da VPC (VPC CNI)

    Referências: Metrics Server no EKS · Amazon VPC CNI.

    Observabilidade: Container Insights

    • O add-on Amazon CloudWatch Observability instala o agente do CloudWatch e o Fluent Bit nos nós.
    • O Container Insights mostra CPU, memória, rede e reinícios por cluster, nó, namespace e Pod, e os logs dos containers vão para o CloudWatch Logs.
    • Junto com os logs do control plane ligados no cluster.yaml (API, audit, scheduler…), dá para investigar desde o Pod até as decisões do control plane.

    Referência: Container Insights com o add-on CloudWatch Observability.

    Prática
    Exercício 5.4.1

    Deploy, exposição, escala e rollback da Loja no EKS

    ~25 min

    Implantar a Loja num namespace, expor com um Service LoadBalancer da AWS, escalar, trocar de versão e fazer rollback para uma revisão específica.

    Antes de começar

    Usa o cluster aula5 do exercício 5.1.1. Trabalhe em ~/eks/aula-5. O load balancer criado aqui é removido no exercício 5.5.1.

    1. Crie o namespace da Loja e use-o como padrão:

      terminal
      cd ~/eks/aula-5 && kubectl create namespace loja && kubectl config set-context --current --namespace=loja

      Crie o manifesto do Deployment, com a página Deploy V1!:

      terminal
      cat > deployment.yaml <<'EOF'
apiVersion: apps/v1
kind: Deployment
metadata:
  name: loja
spec:
  replicas: 3
  selector:
    matchLabels:
      app: loja
  strategy:
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
  template:
    metadata:
      labels:
        app: loja
    spec:
      containers:
        - name: nginx
          image: nginx:1.30.6-alpine
          command: ["sh", "-c"]
          args: ["echo '<h1>Deploy V1!</h1>' > /usr/share/nginx/html/index.html && exec nginx -g 'daemon off;'"]
          ports:
            - containerPort: 80
          readinessProbe:
            httpGet: { path: /, port: 80 }
            periodSeconds: 3
          resources:
            requests: { cpu: 50m, memory: 64Mi }
            limits: { memory: 128Mi }
EOF

      Aplique e confira onde os Pods foram parar (repare nos IPs da VPC):

      terminal
      kubectl apply -f deployment.yaml && kubectl rollout status deployment/loja && kubectl get pods -o wide

    2. Crie o Service do tipo LoadBalancer:

      terminal
      cat > service.yaml <<'EOF'
apiVersion: v1
kind: Service
metadata:
  name: loja
spec:
  type: LoadBalancer
  selector:
    app: loja
  ports:
    - protocol: TCP
      port: 80
      targetPort: 80
EOF
kubectl apply -f service.yaml

      Aguarde o EXTERNAL-IP virar um nome ….elb.amazonaws.com (Ctrl+C sai):

      terminal
      kubectl get svc loja -w

      Veja o load balancer pelo lado da AWS:

      terminal
      aws elb describe-load-balancers --query 'LoadBalancerDescriptions[].[DNSName,Scheme,length(Instances)]' --output table

      Chame a Loja pelo DNS do load balancer (o DNS pode levar de 1 a 3 minutos para responder):

      terminal
      LB=$(kubectl get svc loja -o jsonpath='{.status.loadBalancer.ingress[0].hostname}'); until curl -s --max-time 5 http://$LB; do echo "aguardando o load balancer..."; sleep 10; done

      Abra o mesmo endereço no navegador:

      terminal
      echo "http://$LB"

    3. Escale para 8 réplicas e veja onde elas foram parar:

      terminal
      kubectl scale deployment loja --replicas=8 && kubectl rollout status deployment/loja && kubectl get pods -o wide

      Veja o consumo pelo metrics-server (add-on do EKS):

      terminal
      kubectl top nodes; kubectl top pods

      Volte para 3 réplicas:

      terminal
      kubectl scale deployment loja --replicas=3

    4. Publique a versão 2 trocando só o texto da página, e anote o motivo:

      terminal
      sed 's/Deploy V1!/Deploy V2!/' deployment.yaml > deployment-v2.yaml && kubectl apply -f deployment-v2.yaml && kubectl annotate deployment loja kubernetes.io/change-cause="pagina V2" --overwrite && kubectl rollout status deployment/loja

      Confira a página nova:

      terminal
      curl -s http://$LB

      Veja o histórico de revisões:

      terminal
      kubectl rollout history deployment/loja

      Volte para a revisão 1:

      terminal
      kubectl rollout undo deployment/loja --to-revision=1 && kubectl rollout status deployment/loja && curl -s http://$LB
    Resultado esperado
    • Os 3 Pods ficam Running nos 2 nós, com IPs 172.31.x.x da VPC.
    • O Service ganha um EXTERNAL-IP como a1b2….us-east-1.elb.amazonaws.com, e o describe-load-balancers mostra um Classic Load Balancer internet-facing com os 2 nós registrados.
    • O curl e o navegador mostram Deploy V1!; com 8 réplicas, os Pods se dividem entre os nós; o kubectl top mostra CPU e memória.
    • Depois do v2, a página mostra Deploy V2!; o histórico tem as revisões 1 e 2 e, depois do undo --to-revision=1, a página volta a Deploy V1! (e a revisão 1 vira a 3).
    O que aprendemos com este exercício?
    • Os mesmos manifestos e comandos da Aula 04 funcionam no EKS: é a portabilidade do Kubernetes na prática.
    • Um Service LoadBalancer no EKS cria um load balancer real da AWS, com DNS público, sem nenhum passo no console.
    • O rollback pode voltar para qualquer revisão guardada, não só para a anterior.
    • Com o VPC CNI, os Pods recebem IPs da VPC e o load balancer alcança os nós pela NodePort.
    O curl não responde depois de 5 minutos?

    Veja os eventos com kubectl describe svc loja. Se o load balancer estiver criado mas sem instâncias saudáveis (aws elb describe-instance-health --load-balancer-name ${LB%%-*}), libere as NodePorts para o security group do load balancer no security group do cluster:

    terminal
    ELB_SG=$(aws elb describe-load-balancers --load-balancer-names ${LB%%-*} --query 'LoadBalancerDescriptions[0].SecurityGroups[0]' --output text)
CLUSTER_SG=$(aws eks describe-cluster --name aula5 --query cluster.resourcesVpcConfig.clusterSecurityGroupId --output text)
aws ec2 authorize-security-group-ingress --group-id $CLUSTER_SG --protocol tcp --port 30000-32767 --source-group $ELB_SG
    Desafio

    Aplique um HPA (o mesmo YAML do exercício 4.8.1, apontando para loja, com alvo de 50% de CPU) e confira com kubectl get hpa que as métricas chegam pelo add-on metrics-server do EKS.

    Boas práticas e encerramento

    Conceito
    Capítulo 5 · Do laboratório à produção

    O cluster funciona. E agora, como operar?

    A Loja está no EKS, atrás de um load balancer da AWS. Para chegar à produção, falta transformar o que foi feito no terminal em processo: código versionado, upgrades planejados, segurança e custo sob controle. E, no laboratório, não deixar nada ligado.

    Práticas recomendadas

    Infra como código

    eksctl, Terraform ou CloudFormation para o cluster; GitOps (Argo CD, Flux) para os workloads. Nada manual no console: evita drift.

    Upgrades

    Uma minor por vez, dentro dos 14 meses de suporte padrão. Leia as APIs removidas (tópico 4.11 da Aula 04), comece por dev/staging e atualize control plane, add-ons e nós, nessa ordem.

    Segurança

    Endpoint privado ou restrito, access entries com mínimo privilégio, Pod Identity para os Pods, Pod Security Standards, imagens escaneadas (Trivy, Aula 01).

    Custo e tamanho

    Requests calibrados (VPA em Off), Karpenter ou CAS para os nós, spot onde couber, e limite de Pods por nó do VPC CNI.

    Referências: EKS Best Practices Guide · Update existing cluster.

    Exercício 5.5.1

    Encerrando o laboratório sem deixar custo

    ~15 min

    Remover o load balancer, apagar o cluster e o node group com eksctl e conferir na AWS que não sobrou nada.

    Antes de começar

    Usa o cluster aula5 e os recursos dos exercícios 5.1.1 a 5.4.1. Se a sessão do Learner Lab expirou, inicie de novo e atualize as credenciais como no passo 1 do exercício 5.1.1.

    1. Apague o namespace da Loja. O Service LoadBalancer vai junto, e o EKS remove o Classic Load Balancer:

      terminal
      cd ~/eks/aula-5 && kubectl delete namespace loja

      Confira que o load balancer sumiu (pode levar 1 ou 2 minutos):

      terminal
      sleep 60; aws elb describe-load-balancers --query 'LoadBalancerDescriptions[].DNSName' --output text

    2. Apague o cluster, o node group e os add-ons. O --wait espera as pilhas do CloudFormation terminarem (10 a 15 minutos):

      terminal
      eksctl delete cluster -f cluster.yaml --wait

    3. Confira que não sobrou cluster, pilha, instância nem interface do EKS:

      terminal
      aws eks list-clusters --output text
aws cloudformation list-stacks --stack-status-filter CREATE_COMPLETE DELETE_FAILED --query 'StackSummaries[?contains(StackName,`aula5`)].StackName' --output text
aws ec2 describe-instances --filters Name=tag:eks:cluster-name,Values=aula5 Name=instance-state-name,Values=pending,running --query 'Reservations[].Instances[].InstanceId' --output text
aws ec2 describe-network-interfaces --filters Name=description,Values="Amazon EKS aula5*" --query 'NetworkInterfaces[].NetworkInterfaceId' --output text

      Remova o contexto do cluster apagado do seu kubeconfig:

      terminal
      kubectl config delete-context $(kubectl config current-context)

    4. No AWS Academy, clique em End Lab. Em github.com/codespaces, pare o codespace (… → Stop codespace).

    Resultado esperado
    • Depois do delete namespace, o describe-load-balancers não lista mais o load balancer da Loja.
    • O eksctl delete cluster apaga as pilhas eksctl-aula5-nodegroup-ng-loja e eksctl-aula5-cluster e termina sem erro.
    • Os quatro comandos de conferência não imprimem nada: nenhum cluster, pilha, instância ou ENI do aula5.
    O que aprendemos com este exercício?
    • A ordem importa: apagar o Service primeiro deixa o próprio EKS remover o load balancer que criou.
    • O eksctl desfaz o que criou pelas mesmas pilhas do CloudFormation: o cluster como código também é apagado como código.
    • Na nuvem, encerrar e conferir faz parte do exercício: recurso esquecido é custo.
