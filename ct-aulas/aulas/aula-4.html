    4.1

    Por que Kubernetes

    Conceito

    O que é o Kubernetes

    Uma plataforma open source para gerenciar workloads e serviços em containers, com configuração declarativa e automação. O nome vem do grego: timoneiro, piloto. A abreviação K8s conta as oito letras entre o “K” e o “s”.

    Declarativo

    Você descreve o estado desejado (“3 cópias da loja, versão 2”). O Kubernetes trabalha sem parar para que o estado atual chegue nele.

    Self-healing

    Reinicia containers que falham, substitui Pods de nós que caem e só manda tráfego para quem está pronto.

    Portável

    O mesmo manifesto roda num laptop, on-premises, na AWS (EKS), no Google (GKE) ou na Azure (AKS).

    Extensível

    A API aceita tipos novos (CRDs) e controllers próprios. É assim que nascem Gateway API, Argo CD, operadores de banco…

    Referência: kubernetes.io · Overview.

    De onde veio: Borg, Docker e um commit em 2014

    Referências: 10 Years of Kubernetes · kubernetes.io · Releases.

    Quando usar (e quando não)

    A favor

    • Alta disponibilidade e self-healing.
    • Escala horizontal, rollout e rollback de versões.
    • Portabilidade entre clouds e on-premises.
    • Ecossistema enorme (CNCF) e API extensível.

    Contra

    • Complexidade: montar, operar e atualizar exige conhecimento e tempo.
    • Custo: o cluster consome recursos só para existir.
    • Atualizações: 3 versões por ano; APIs mudam.

    Meio-termo

    Kubernetes gerenciado (Amazon EKS, Google GKE, Azure AKS): o provedor cuida do control plane. Para um sistema pequeno, um ECS, um App Runner ou até um Compose podem bastar.

    Na históriaA Loja tem vários times (vitrine, carrinho, pagamento), precisa rodar na AWS e num data center de um parceiro, e quer canary nas releases. É o perfil em que o Kubernetes compensa o custo.

    Quem cuida de quem

    Antes de colocar a Loja no Kubernetes, o time abre a caixa: quem guarda o estado, quem decide onde cada container roda, quem percebe que algo morreu. Cada peça tem um papel só, e todas conversam pelo mesmo lugar: a API.

    Pods, nós e cluster

    Pod

    A menor unidade que você implanta: um ou mais containers com rede e armazenamento compartilhados. O Kubernetes gerencia Pods, não containers.

    Nó (node)

    Uma máquina, física ou virtual, que fornece CPU e memória para os Pods. Nós de tamanhos diferentes comportam quantidades diferentes de Pods.

    Cluster

    O conjunto de nós, gerenciado como um só. Em produção, o control plane roda em várias máquinas, em zonas diferentes.

    Os componentes, um a um

    Os próximos slides abrem cada peça do diagrama anterior: o que faz, com quem conversa e onde aparece no seu cluster kind. Os ícones seguem a legenda oficial do Kubernetes.

    • Control plane: API server, etcd, scheduler, controller manager e, na cloud, o cloud controller manager.
    • Node: kubelet, kube-proxy e o container runtime.
    • Regra de ouro: todos falam com o API server, e só com ele.

    Referência: kubernetes.io · Cluster Architecture.

    Control plane: o cérebro do cluster

    O conjunto de componentes que gerencia o estado do cluster: guarda o que foi pedido, decide onde cada Pod roda e reage a mudanças.

    • Em clusters simples, tudo fica numa máquina que não roda aplicações. Em produção, em várias máquinas e zonas.
    • Pode rodar como serviços do sistema, como static Pods (kubeadm, kind) ou ser gerenciado pelo provedor (EKS, GKE, AKS).
    • No kind: tudo dentro do container aula4-control-plane.

    Referência: Cluster Architecture · Control plane deployment options.

    kube-apiserver: a porta de entrada

    O front end do control plane: expõe a API HTTP do Kubernetes. Tudo é uma chamada a ela: um kubectl get, um controller criando Pods, o kubelet informando status.

    • Modelo hub-and-spoke: as chamadas dos nós e dos Pods terminam no API server; os outros componentes do control plane não expõem serviços remotos.
    • Os clientes usam watch: em vez de perguntar o tempo todo, recebem as mudanças.
    • Escala na horizontal: várias instâncias atrás de um balanceador.

    Referências: kube-apiserver · Communication between Nodes and the Control Plane · API Concepts (watch).

    etcd: a memória do cluster

    Banco chave-valor consistente e altamente disponível, onde o Kubernetes guarda todos os dados do cluster: cada objeto, seu spec e seu status.

    • Usa o algoritmo Raft: um líder replica cada gravação; ela só vale com a maioria (quórum).
    • Número ímpar de membros: 3 toleram 1 falha; 5 toleram 2.
    • O API server grava sob o prefixo /registry (flag --etcd-prefix).
    • Perdeu o etcd, perdeu o cluster: tenha backup.

    Referências: etcd no Kubernetes · etcd FAQ (quórum e tolerância a falhas) · kube-apiserver --etcd-prefix.

    kube-scheduler: onde cada Pod vai morar

    Observa os Pods novos sem nó e escolhe um nó para cada um. Ele só decide: quem cria o container é o kubelet do nó escolhido.

    • Filtragem: descarta nós onde o Pod não cabe (CPU e memória pedidas, taints, nodeSelector…).
    • Pontuação: dá nota aos nós que sobraram e escolhe o de maior nota.
    • Binding: avisa o API server da decisão. Nenhum nó serve? O Pod fica Pending.

    Referências: kube-scheduler · Kubernetes Scheduler (filtering e scoring).

    kube-controller-manager: os controllers num processo só

    Roda os controllers: loops que comparam o estado desejado com o atual e agem pela API até os dois baterem.

    • Logicamente, cada controller é um processo separado; para simplificar, todos são compilados num binário único e rodam num processo só.
    • Exemplos: Node (percebe nós que caem), Job, EndpointSlice (liga Services a Pods), ServiceAccount (cria a default em cada namespace).
    • Com várias réplicas do control plane, só uma fica ativa: leader election por um Lease.

    Referências: kube-controller-manager · Leases (leader election).

    cloud-controller-manager: a ponte com a cloud

    Opcional. Concentra a lógica específica de cada cloud e liga o cluster à API do provedor. Roda só os controllers que dependem da cloud.

    • Node controller: preenche o Node com dados da VM e apaga o Node quando a VM some.
    • Route controller: rotas na rede da cloud para Pods em nós diferentes.
    • Service controller: cria o load balancer de cada Service LoadBalancer.
    • On-premises ou no seu PC, ele não existe. No tópico 4.6 você roda o cloud-provider-kind, que faz esse papel para o kind.

    Referências: cloud-controller-manager · Cloud Controller Manager.

    Node: onde as aplicações rodam

    Uma máquina, física ou virtual, que roda os Pods. Todo nó tem três componentes: kubelet, kube-proxy (opcional) e o container runtime.

    • Cada nó também é um objeto na API (kind: Node), com capacidade, endereços e condições como Ready.
    • O kubelet manda heartbeats atualizando um Lease no namespace kube-node-lease: é assim que o control plane sabe que o nó está vivo.
    • No kind: os containers aula4-worker e aula4-worker2.

    Referências: Nodes · Leases (node heartbeats).

    kubelet: o agente de cada nó

    Agente que roda em todo nó e garante que os containers descritos nos PodSpecs estão rodando e saudáveis.

    • Recebe os Pods atribuídos ao seu nó pelo API server; também lê static Pods de uma pasta local (é assim que o kind sobe o control plane).
    • Fala com o runtime pela CRI (gRPC): containerd ou CRI-O. O Docker Engine saiu na v1.24.
    • Roda as probes, reinicia containers e reporta o status do Pod.
    • Não gerencia containers que o Kubernetes não criou.

    Referências: kubelet · Static Pods · CRI · Container Runtimes.

    kube-proxy: as regras de rede dos Services

    Opcional. Roda em cada nó e implementa parte do conceito de Service: mantém regras de rede que levam o tráfego do IP virtual do Service até os Pods.

    • Observa Services e EndpointSlices pela API e reescreve as regras do nó.
    • Modos no Linux: iptables (padrão na v1.37), nftables e ipvs (depreciado desde a v1.35).
    • Alguns plugins de rede (ex.: Cilium) fazem esse trabalho e dispensam o kube-proxy.

    Referências: kube-proxy · Virtual IPs and Service Proxies.

    Resumo: o papel de cada componente

    Control plane

    • kube-apiserver: porta de entrada. Tudo passa pela API.
    • etcd: chave-valor com todo o estado do cluster.
    • kube-scheduler: escolhe o nó de cada Pod.
    • kube-controller-manager: um binário com vários controllers.
    • cloud-controller-manager (opcional): integra com a cloud.

    Nodes (data plane)

    • kubelet: garante os containers dos Pods do nó.
    • container runtime: containerd ou CRI-O, via CRI.
    • kube-proxy (opcional): regras de rede dos Services.

    Addons

    • DNS: CoreDNS dá nome aos Services (web.app.svc.cluster.local).
    • Rede dos Pods (CNI): kindnet no kind; Calico, Cilium, VPC CNI na AWS.
    • Métricas: metrics-server alimenta kubectl top e o HPA.

    Referência: Cluster Architecture.

    Controllers: o loop de controle

    • É o princípio do termostato: você define a temperatura desejada; ele liga e desliga o equipamento até a temperatura atual chegar lá.
    • Cada controller cuida de um tipo de objeto e age só pelo kube-apiserver.
    • Um controller pode criar objetos que outro cuida: o Deployment cria ReplicaSets, o ReplicaSet cria Pods.

    Referência: kubernetes.io · Controllers.

    node-lifecycle-controller

    Vigia a saúde dos nós pelos heartbeats que o kubelet envia.

    • Por padrão, confere o estado de cada nó a cada 5 segundos.
    • Nó sem resposta: a condição Ready vira Unknown.
    • Continuou sem resposta: os Pods do nó são despejados (por padrão, 5 minutos depois).

    Referência: Nodes.

    node-ipam-controller

    Atribui a cada nó novo um bloco de IPs (CIDR) para os Pods.

    • Age quando o nó é registrado no cluster.
    • Só funciona se a atribuição de CIDR estiver ligada.
    • Os Pods do nó recebem IPs desse bloco.

    Referência: Nodes.

    Node e Route controllers (cloud)

    Node controller

    • Preenche o Node com dados da cloud: identificador (providerID), região, zona, endereços.
    • Nó sem resposta: pergunta à cloud se a máquina ainda existe.
    • Máquina removida da cloud: apaga o Node do cluster.

    Route controller

    • Cada nó tem um bloco de IPs de Pods (podCIDR).
    • A tabela de rotas da cloud aprende para qual nó mandar cada bloco: 10.244.1.0/24 → worker-1.
    • Sem essas rotas, um Pod no worker-1 não alcança um Pod no worker-2 (quando a rede depende delas).

    O terceiro, o Service controller, aparece no tópico 4.6, quando um Service LoadBalancer ganha um IP externo no kind.

    Referência: Cloud Controller Manager.

    Exercício 4.2.1

    Criando um cluster com kind e encontrando cada componente

    ~25 min

    Instalar o kind, criar um cluster com 1 control plane e 2 workers, e localizar no cluster cada componente da arquitetura: static Pods, kubelet, runtime, Leases e kubeconfig.

    Antes de começar

    Use um codespace novo de 4 cores. Este exercício cria o cluster aula4; os seguintes desta aula usam o mesmo cluster, e o 4.7.1 apaga tudo.

    1. Baixe o kind v0.33.0 (passos de kind · Installation and usage):

      terminal
      [ $(uname -m) = x86_64 ] && curl -Lo ./kind https://kind.sigs.k8s.io/dl/v0.33.0/kind-linux-amd64

      Torne-o executável e mova para o PATH:

      terminal
      chmod +x ./kind && sudo mv ./kind /usr/local/bin/kind

      Confira a versão:

      terminal
      kind version

      Confira o kubectl (a imagem padrão do Codespaces já traz):

      terminal
      kubectl version --client

      Só se o kubectl não existir, baixe a versão stable e instale:

      terminal
      curl -LO "https://dl.k8s.io/release/$(curl -Ls https://dl.k8s.io/release/stable.txt)/bin/linux/amd64/kubectl" && sudo install -m 0755 kubectl /usr/local/bin/kubectl && rm kubectl

    2. Crie a pasta da aula e entre nela:

      terminal
      mkdir -p ~/k8s/aula-4 && cd ~/k8s/aula-4

      Descreva o cluster: 1 control plane e 2 workers:

      terminal
      cat > kind-cluster.yaml <<'EOF'
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
nodes:
  - role: control-plane
  - role: worker
  - role: worker
EOF

      Crie o cluster aula4 e espere o control plane ficar pronto:

      terminal
      kind create cluster --name aula4 --config kind-cluster.yaml --wait 5m

    3. Veja qual contexto o kubectl está usando e as versões de cliente e servidor:

      terminal
      kubectl config current-context; kubectl version

      Veja o que o kind gravou no kubeconfig (repare no server: https://127.0.0.1:…):

      terminal
      kubectl config view --minify

      Crie um atalho para o resto da aula:

      terminal
      alias k=kubectl

    4. Liste os nós, com o runtime e o IP de cada um:

      terminal
      kubectl get nodes -o wide

      Veja os mesmos nós por fora: cada um é um container Docker:

      terminal
      docker ps --filter name=aula4 --format 'table {{.Names}}\t{{.Image}}\t{{.Ports}}'

      Veja o bloco de IPs de Pods que cada nó recebeu (trabalho do node-ipam-controller):

      terminal
      kubectl get nodes -o custom-columns=NODE:.metadata.name,POD_CIDR:.spec.podCIDR

    5. Encontre os componentes, que rodam como Pods no namespace kube-system. A coluna NODE mostra onde cada um está:

      terminal
      kubectl get pods -n kube-system -o wide

      Veja de onde vêm os componentes do control plane: os manifestos de static Pods que o kubelet lê:

      terminal
      docker exec aula4-control-plane ls /etc/kubernetes/manifests

      O kubelet não é Pod: é um serviço do sistema dentro do nó:

      terminal
      docker exec aula4-worker systemctl is-active kubelet containerd

      Pergunte ao runtime de um worker quais containers ele está rodando:

      terminal
      docker exec aula4-worker crictl ps

    6. Veja os heartbeats dos nós (um Lease por nó) e a saúde do API server:

      terminal
      kubectl get leases -n kube-node-lease
      terminal
      kubectl get --raw='/readyz?verbose' | tail -5

      Veja quem é o líder do scheduler e do controller manager (leader election):

      terminal
      kubectl get leases -n kube-system
    Resultado esperado
    • kubectl config current-context responde kind-aula4; o kubectl version mostra o servidor v1.37.0.
    • Três nós Ready: aula4-control-plane (papel control-plane), aula4-worker e aula4-worker2, com runtime containerd://… e um POD_CIDR diferente cada (10.244.x.0/24).
    • etcd, kube-apiserver, kube-controller-manager e kube-scheduler rodam só em aula4-control-plane, e a pasta de manifestos tem um .yaml para cada um; kube-proxy e kindnet aparecem uma vez em cada nó; coredns tem 2 réplicas.
    • systemctl responde active duas vezes; crictl ps lista containers como kube-proxy e kindnet-cni.
    • Há 3 Leases em kube-node-lease, um por nó; o /readyz termina em readyz check passed; em kube-system aparecem os Leases kube-scheduler e kube-controller-manager.
    O que aprendemos com este exercício?
    • Um cluster é um conjunto de nós com papéis diferentes: o control plane gerencia, os workers rodam as aplicações.
    • Num cluster kubeadm (como o kind), o control plane roda como static Pods que o kubelet lê de uma pasta; o kubelet em si é um serviço do sistema.
    • O kubectl só alcança o cluster pelo kubeconfig, e o contexto diz qual cluster está em uso.
    • Quem roda os containers é o runtime (containerd), comandado pelo kubelet; a saúde dos nós chega ao control plane pelos Leases.

    4.3

    Pods e manifestos YAML

    Conceito
    Capítulo 3 · O primeiro Pod da Loja

    Você não roda containers; você declara Pods

    No Docker, o time digitava docker run. No Kubernetes, ninguém “executa” nada: escreve um manifesto dizendo o que quer, entrega à API e acompanha o cluster convergir. O primeiro passo é aprender a língua desses manifestos.

    YAML em dois tipos de dado

    Lista (sequence)

    Cada item começa com -. A ordem importa.

    compras.yaml
    - leite
- pão
- café

    Dicionário (mapping)

    Pares chave: valor. A ordem não importa.

    sorvete.yaml
    sabor: chocolate
vegano: true
calorias: 1000

    Os dois se aninham, e a indentação (espaços, nunca tab) indica a quem cada linha pertence. Um espaço fora do lugar muda o significado ou invalida o arquivo.

    sorvete.yaml
    sorvete:
  sabor: chocolate
  coberturas:
    - granulado
    - calda

    A estrutura de todo manifesto

    • apiVersion: qual API entende esse objeto. O Pod está na v1.
    • kind: o tipo do objeto. Diferencia maiúsculas: Pod, nunca pod.
    • metadata: nome, namespace, labels.
    • spec: o que você quer. Em containers, o - mostra que é uma lista: cabe mais de um.

    Não escreva do zero: parta dos exemplos da documentação e ajuste. O nome da imagem é onde mais aparecem erros de digitação.

    Referência: kubernetes.io · Objects In Kubernetes.

    Um Pod por dentro

    Um Pod é um grupo de um ou mais containers que compartilham rede e armazenamento e sempre rodam juntos, no mesmo nó.

    • Um IP por Pod: os containers se falam por localhost.
    • Volumes do Pod podem ser montados em vários containers.
    • Init containers rodam antes, até terminar; sidecars acompanham o container principal (logs, proxy).
    • O caso mais comum: um container por Pod.

    Referências: Pods · Init Containers · Sidecar Containers.

    As fases de um Pod

    • Pending: aceito, mas ainda sem rodar: esperando nó ou baixando a imagem.
    • Running: está num nó e ao menos um container roda (ou reinicia).
    • Succeeded: todos terminaram com sucesso e não vão reiniciar.
    • Failed: todos terminaram e ao menos um falhou.
    • Unknown: o estado não pôde ser obtido; em geral, falha de comunicação com o nó.

    CrashLoopBackOff e Terminating aparecem no kubectl, mas não são fases: são textos de exibição.

    Referência: Pod Lifecycle.

    restartPolicy e o CrashLoopBackOff

    • restartPolicy: Always (padrão), OnFailure ou Never.
    • O container caiu? O kubelet reinicia no mesmo Pod e no mesmo nó, com espera exponencial: 10 s, 20 s, 40 s… até o teto de 300 s (5 min).
    • Rodou 10 minutos sem problemas: a contagem zera.
    • Enquanto espera, o kubectl get pods mostra CrashLoopBackOff e a coluna RESTARTS sobe.
    • Para ver o erro do container que morreu: kubectl logs --previous.

    Referência: Pod Lifecycle · Container restart policy.

    Namespaces, recursos e cotas

    Conceito
    Capítulo 4 · Três times, um cluster

    Cada um no seu espaço

    Vitrine, carrinho e pagamento vão dividir o mesmo cluster. Sem regras, um Pod mal configurado do carrinho consome toda a memória e derruba a vitrine. O time de plataforma separa o cluster em namespaces e coloca um teto em cada um.

    Separando o cluster em partes

    Namespaces isolam grupos de objetos dentro do mesmo cluster. Os nomes precisam ser únicos dentro de um namespace, não entre eles. Comandos sem -n olham só o namespace atual: por isso kubectl get pods pode dizer que não há nada enquanto o cluster está cheio de Pods.

    Namespace inicialPara quê
    defaultPara começar sem criar um namespace. Em produção, crie os seus.
    kube-systemObjetos criados pelo próprio Kubernetes.
    kube-publicLegível por todos os clientes, inclusive não autenticados.
    kube-node-leaseOs Leases dos nós: os heartbeats que você viu no exercício 4.2.1.

    Referência: kubernetes.io · Namespaces.

    Namespace é parte do endereço

    • No manifesto: metadata.namespace: vitrine. No comando: -n vitrine. Em todos: -A.
    • Fixe um padrão no contexto: kubectl config set-context --current --namespace=vitrine.
    • O DNS de um Service inclui o namespace: web.vitrine.svc.cluster.local.
    • É a fronteira para cotas e permissões (RBAC). Nós e PersistentVolumes não têm namespace.

    Referências: Namespaces · DNS for Services and Pods.

    requests e limits: reservar e limitar

    • requests: quanto o container precisa. O scheduler usa esse valor para escolher um nó com espaço.
    • limits: o máximo que ele pode usar. Quem garante é o kubelet e o kernel do nó.
    • Passou do limite de CPU: é estrangulado (throttling). Passou do limite de memória: pode ser morto (OOMKilled).
    • Unidades: 250m = um quarto de CPU; 128Mi = 128 mebibytes.

    Referência: Resource Management for Pods and Containers.

    Classes de QoS: quem sai primeiro

    A partir de requests e limits, o Kubernetes classifica cada Pod. Quando o nó fica sem memória, o kubelet despeja primeiro os de menor classe.

    ClasseQuandoNa falta de recurso
    GuaranteedTodo container tem request e limit de CPU e memória, com request = limit.Últimos a sair.
    BurstableAlgum request ou limit definido, sem atender ao Guaranteed.Saem depois dos BestEffort.
    BestEffortNenhum request nem limit.Primeiros a sair.

    Veja a classe de um Pod em status.qosClass. Em produção, defina sempre ao menos os requests.

    Referência: Pod Quality of Service Classes.

    ResourceQuota e LimitRange

    ResourceQuota

    Teto do namespace inteiro: soma de CPU, memória, número de Pods, Services, PVCs…

    Com cota de cpu e memory, todo Pod novo precisa declarar requests ou limits desses recursos; senão, a criação é recusada.

    LimitRange

    Regras por container num namespace: mínimo, máximo e valores padrão de requests e limits.

    Com um LimitRange de defaults, Pods sem recursos declarados recebem valores e passam pela cota.

    yaml
    apiVersion: v1
kind: ResourceQuota
metadata:
  name: vitrine-quota
  namespace: vitrine
spec:
  hard:
    cpu: "1"
    memory: 1Gi
    pods: "10"

    Referências: Resource Quotas · Limit Ranges.

    namespace-controller

    Quando um namespace é apagado, apaga tudo o que está dentro dele.

    • A exclusão é assíncrona: o namespace fica em Terminating enquanto esvazia.
    • Pods, Services, ConfigMaps, Secrets: tudo do namespace vai junto.
    • Só no fim o namespace some.

    Referência: Namespaces.

    serviceaccount-controller

    Garante que exista uma ServiceAccount chamada default em todo namespace ativo.

    • Namespace novo: a default aparece em seguida.
    • Pods que não escolhem uma ServiceAccount usam a default.
    • ServiceAccount é a identidade do Pod para falar com a API.

    Referência: Managing Service Accounts.

    resourcequota-controller

    Calcula quanto cada ResourceQuota já foi usada no namespace.

    • Soma os requests e limits dos objetos do namespace.
    • Grava o total em Used, ao lado do teto Hard.
    • Quem recusa um Pod acima da cota é o admission do API server; este controller mantém a conta.

    Referência: Resource Quotas.

    Deployments e os outros workloads

    Conceito
    Capítulo 5 · A loja não pode cair

    Pod solto não se defende sozinho

    No exercício anterior, o Pod apagado não voltou. Se o nó dele cair na Black Friday, a vitrine some. A Loja precisa de alguém que mantenha 3 cópias vivas, troque a versão sem derrubar ninguém e volte atrás se der errado: um Deployment.

    A hierarquia dos workloads

    Deploymentversões, rolling update, rollback
    →
    ReplicaSetmantém N réplicas de um template
    →
    Pod1+ containers com IP e volumes compartilhados
    • Pod é a menor unidade e é descartável: nunca crie Pods soltos em produção.
    • O vínculo entre os objetos é feito por labels e selectors (app: web).
    • Cada versão do template gera um novo ReplicaSet. O rollback reativa o anterior.
    • Você quase nunca mexe no ReplicaSet: mexe no Deployment, e ele cuida do resto.

    Referência: Deployments.

    Anatomia de um Deployment

    yaml
    apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3              # quantas cópias
  selector:                # quais Pods são meus
    matchLabels:
      app: web
  strategy:
    type: RollingUpdate    # padrão
    rollingUpdate:
      maxSurge: 25%        # padrão
      maxUnavailable: 25%  # padrão
  template:                # a receita do Pod
    metadata:
      labels:
        app: web           # tem que bater com o selector
    spec:
      containers:
        - name: nginx
          image: nginx:1.28-alpine
    • replicas: o estado desejado. Escalar é mudar esse número.
    • selector: como o Deployment acha seus Pods. Precisa bater com os labels do template.
    • template: um Pod sem nome. Mudou qualquer coisa nele (imagem, env, recursos)? É uma nova revisão e um rollout começa.
    • Mudar só replicas não cria revisão.
    • strategy: RollingUpdate (troca aos poucos) ou Recreate (derruba tudo e sobe de novo).

    Referência: Deployments · apps/v1.

    deployment-controller

    Cuida dos Deployments: para cada um, cria e ajusta os ReplicaSets.

    • Mudou a receita do Pod (ex.: a imagem): cria um ReplicaSet novo.
    • Sobe o novo e desce o antigo aos poucos: é o rolling update.
    • O ReplicaSet antigo fica com 0 réplicas, pronto para um rollback.

    Referência: Deployments.

    replicaset-controller

    Mantém o número de Pods de cada ReplicaSet igual ao pedido.

    • Faltou Pod (caiu, foi apagado, o nó sumiu): cria outro.
    • Sobrou Pod: apaga o excedente.
    • Acha os seus Pods pelo selector de labels.

    Referência: ReplicaSet.

    Rolling update passo a passo

    Com 4 réplicas e os padrões de 25%:

    • maxSurge: 25% → até 1 Pod a mais: no máximo 5 ao mesmo tempo.
    • maxUnavailable: 25% → até 1 a menos: no mínimo 3 disponíveis.
    • O Pod novo só conta como disponível quando fica Ready. Imagem quebrada? O rollout trava aqui, e as réplicas antigas continuam atendendo.
    • Os percentuais são arredondados: o surge para cima, o unavailable para baixo.

    Referência: Deployments · Rolling Update.

    Revisões, histórico e rollback

    ComandoO que faz

    Referências: Rolling Back a Deployment · kubectl rollout.

    garbage-collector-controller

    Apaga objetos dependentes cujo dono não existe mais.

    • Objetos criados por outro registram o dono (owner reference).
    • O ReplicaSet tem o Deployment como dono; o Pod tem o ReplicaSet.
    • Apagou o dono: os dependentes são removidos em cascata.

    Referência: Garbage Collection.

    ttl-after-finished-controller

    Apaga Jobs terminados depois de um tempo, para não acumularem no cluster.

    • Vale só para Jobs, completos ou com falha.
    • O tempo vem do campo ttlSecondsAfterFinished do Job.
    • Apagar o Job apaga também os Pods dele.

    Services, Ingress e Gateway API

    Conceito

    Como achar quem muda de endereço?

    A vitrine roda com 3 réplicas, mas cada Pod recriado ganha um IP novo. O carrinho precisa de um endereço que não mude, e os clientes precisam de uma porta de entrada única na internet. E, na próxima release, o time quer mandar só 20% do tráfego para a versão nova.

    Service: um endereço estável para Pods efêmeros

    • O Service ganha um IP virtual fixo e um nome no DNS do cluster.
    • Acha os Pods pelo selector (app: web), não por IP.
    • Só Pods Ready recebem tráfego. Pod morreu e voltou com outro IP? O Service segue o mesmo.
    • No mesmo namespace, basta o nome: http://web. De outro: web.app ou web.app.svc.cluster.local.

    Referências: Service · DNS for Services and Pods.

    • É a opção indicada na documentação do kind. O projeto ainda se declara em estágio inicial: ótimo para estudo e CI, não para produção.

    4.7

    Health checks: probes

    Conceito
    Capítulo 7 · Rodando não é funcionando

    O Pod está Running, mas a vitrine não responde

    Uma réplica da vitrine travou esperando o banco. O processo continua vivo, o Pod aparece Running e o Service segue mandando clientes para ela. O Kubernetes só sabe o que você ensina a ele perguntar: é para isso que existem as probes.

    Três perguntas diferentes

    ProbePerguntaSe falhar
    startupProbeA aplicação terminou de iniciar?Segura as outras probes; passou do limite, o kubelet reinicia o container
    readinessProbePode receber tráfego agora?O Pod sai dos EndpointSlices do Service (não reinicia)
    livenessProbeEstá vivo ou travado?O kubelet reinicia o container

    Quem executa as probes é o kubelet do nó, no intervalo que você definir. Sem probe nenhuma, o Kubernetes considera o container pronto assim que o processo sobe.

    Referência: Liveness, Readiness, and Startup Probes.

    Quem pergunta e o que acontece com a resposta

    • O kubelet chama a probe no container: HTTP, TCP, gRPC ou um comando.
    • Readiness falhou: o kubelet marca o Pod como não pronto; o endpointslice-controller tira o IP dele do Service. O container segue rodando.
    • Liveness falhou failureThreshold vezes: o kubelet mata e recria o container (RESTARTS sobe).
    • Startup: enquanto não passa, as outras duas nem rodam.

    Referências: Probes · Pod Lifecycle · Container probes.

    A linha do tempo de um Pod com as três probes

    Referência: Liveness, Readiness, and Startup Probes.

    Como configurar uma probe

    yaml
    containers:
  - name: vitrine
    image: nginx:1.30.6-alpine
    startupProbe:
      httpGet: { path: /, port: 80 }
      periodSeconds: 2
      failureThreshold: 30     # até 60 s para subir
    readinessProbe:
      httpGet: { path: /ready.html, port: 80 }
      periodSeconds: 3
    livenessProbe:
      httpGet: { path: /, port: 80 }
      periodSeconds: 5
      failureThreshold: 3      # 3 falhas = restart
    MecanismoPassa quando
    httpGetStatus de 200 a 399
    tcpSocketA porta aceita conexão
    grpcHealth check gRPC responde SERVING
    execO comando sai com código 0

    Ajuste com initialDelaySeconds, periodSeconds, timeoutSeconds, successThreshold e failureThreshold.

    Referências: Configure Liveness, Readiness and Startup Probes · Check mechanisms.

    Armadilhas comuns

    • Liveness que depende do banco: o banco cai e todos os Pods reiniciam em cascata, o que não resolve nada. Liveness checa só o próprio processo.
    • Liveness sem startupProbe em aplicação lenta (JVM, cargas de cache): o Pod é morto antes de subir e entra em CrashLoopBackOff.
    • Readiness igual à liveness: perde-se a chance de tirar o Pod do tráfego sem reiniciá-lo.
    • Endpoints dedicados: /healthz (liveness) e /ready (readiness), como fazem o Spring Actuator e muitas bibliotecas.
    • No ECS (Aula 03), o health check do container e o do target group fazem papéis parecidos.

    Referência: Liveness, Readiness, and Startup Probes.

    4.8

    Autoescala: HPA, KEDA e VPA

    Conceito
    Capítulo 8 · Black Friday

    Meia-noite: o tráfego multiplica por dez

    Na Aula 03, o ECS escalava as tasks por CPU com target tracking. No Kubernetes, a Loja tem três ferramentas diferentes: mais Pods quando a CPU sobe (HPA), mais Pods quando chegam eventos, e zero Pods quando não há nada (KEDA), e Pods do tamanho certo (VPA).

    As dimensões da escala

    • Horizontal (HPA): muda o número de Pods. Mais cópias dividindo a carga.
    • Por eventos (KEDA): alimenta o HPA com métricas externas (fila, cron, Prometheus) e leva a zero quando não há demanda.
    • Vertical (VPA): muda o tamanho de cada Pod (requests e limits).
    • Nós (Cluster Autoscaler, Karpenter): mais Pods precisam de mais máquinas. Esse fica para a Aula 05, no EKS.

    Referências: Autoscaling Workloads · KEDA Concepts.

    Como o HPA funciona por dentro

    • O metrics-server coleta CPU e memória dos kubelets e serve a API metrics.k8s.io. Ele não vem no kind nem no EKS: é instalado à parte.
    • A cada 15 s, o controller do HPA (no kube-controller-manager) lê a métrica, compara com o alvo e ajusta o replicas do Deployment.
    • Percentual de CPU é calculado sobre o request: sem request de CPU, não há HPA por CPU.
    • Variação dentro de 10% (tolerância padrão) não gera ação.

    Referências: Horizontal Pod Autoscaling · metrics-server v0.9.0.

    horizontal-pod-autoscaler-controller

    Ajusta o número de réplicas de acordo com uma métrica, como o uso de CPU.

    • Compara o valor atual da métrica com o alvo.
    • Fórmula: réplicas = ceil(réplicas atuais × valor atual ÷ alvo).
    • As métricas de CPU e memória vêm do metrics-server.

    Referência: Horizontal Pod Autoscaling.

    Configurando um HPA (autoscaling/v2)

    yaml
    apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: php-apache
spec:
  scaleTargetRef:            # quem escalar
    apiVersion: apps/v1
    kind: Deployment
    name: php-apache
  minReplicas: 1
  maxReplicas: 8
  metrics:                   # com base em quê
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 50
  behavior:                  # em que ritmo
    scaleDown:
      stabilizationWindowSeconds: 60
    • scaleTargetRef: Deployment, StatefulSet ou qualquer recurso com o subrecurso scale.
    • metrics: Resource (CPU, memória), Pods e Object (métricas custom) ou External (fora do cluster). Com várias, vence a que pede mais réplicas.
    • behavior: por padrão, sobe na hora e só desce depois de 300 s de estabilização, para não oscilar.
    • Atalho imperativo: kubectl autoscale deployment php-apache --cpu-percent=50 --min=1 --max=8.

    Referência: HPA · Configurable scaling behavior.

    KEDA: escala por eventos, até zero

    • Projeto da CNCF que trabalha junto com o HPA, sem substituí-lo: você cria um ScaledObject e o KEDA cria e gerencia o HPA.
    • O operator faz 0 ↔ 1 (ativa ou desativa o workload); o HPA faz 1 ↔ N com as métricas que o KEDA serve na API external.metrics.k8s.io.
    • Dezenas de scalers: SQS, Kafka, RabbitMQ, Prometheus, cron, CloudWatch…
    • Para tarefas em lote, o ScaledJob cria Jobs em vez de escalar um Deployment.

    Referências: KEDA Concepts · Scaling Deployments · KEDA v2.21.

    Um ScaledObject na prática

    yaml
    apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: promo
spec:
  scaleTargetRef:
    name: promo            # o Deployment
  minReplicaCount: 0       # pode ir a zero
  maxReplicaCount: 10
  cooldownPeriod: 30       # padrão: 300 s
  triggers:
    - type: cron
      metadata:
        timezone: America/Sao_Paulo
        start: 0 0 * * 5       # sexta 00:00
        end: 0 2 * * 5         # sexta 02:00
        desiredReplicas: "8"
    • A promoção da Black Friday abre à meia-noite: 8 réplicas prontas antes do pico, e zero quando acabar.
    • Para ir a zero fora da janela, use minReplicaCount: 0. Colocar desiredReplicas: "0" no cron é quase sempre um erro.
    • A volta a zero espera o cooldownPeriod depois do fim da janela.
    • Com outro gatilho junto (CPU, fila), o valor do cron vira um mínimo dinâmico: o HPA usa o maior.

    Referência: KEDA · Cron scaler.

    VPA: o tamanho certo para cada Pod

    Ajusta requests e limits com base no histórico de uso e em eventos como OOM. É um CRD com três componentes, instalado à parte.

    updateModeO que faz
    OffSó recomenda, no .status. Ótimo para calibrar requests.
    InitialAplica só ao criar Pods.
    RecreateDespeja Pods e recria com o novo tamanho.
    InPlaceOrRecreateRedimensiona sem reiniciar quando dá; senão, despeja.

    Auto está depreciado desde o VPA 1.4.0 (é um alias de Recreate).

    Referências: Vertical Pod Autoscaling · VPA v1.8.0.

    HPAKEDAVPA

    Com base emCPU, memória, métricas customEventos externos: fila, cron, PrometheusHistórico de uso, OOM

    VPA e HPA não devem atuar sobre CPU ou memória ao mesmo tempo: um mexe no request que o outro usa como base. Pode combinar em métricas diferentes (VPA na memória, HPA na CPU) ou HPA em métricas custom.

    Deploy sem downtime

    Conceito
    Capítulo 9 · Release no horário de pico

    Trocar o motor com o avião voando

    A correção do carrinho precisa entrar agora, no meio da Black Friday. O rolling update do tópico 4.5 já troca os Pods aos poucos, mas durante a troca alguns clientes ainda recebem erro 502. Para zerar esses erros, a Loja precisa acertar quatro peças: estratégia, readiness, desligamento gracioso e PDB.

    Onde as requisições se perdem num rollout

    1 · Pod novo cedo demais

    Sem readiness, o Pod entra no Service assim que o processo sobe, antes de a aplicação estar pronta. Correção: readinessProbe.

    2 · Capacidade cai

    Com maxUnavailable alto, sobram poucos Pods para todo o tráfego. Correção: maxSurge: 1, maxUnavailable: 0.

    3 · Pod antigo morre no meio da conversa

    O SIGTERM chega enquanto o Pod ainda recebe tráfego, e a aplicação encerra sem terminar as requisições. Correção: preStop e tratamento de SIGTERM.

    4 · Manutenção derruba tudo

    Um drain de nó tira vários Pods de uma vez. Correção: PodDisruptionBudget e réplicas espalhadas.

    Referência: Deployments · Rolling Update.

    A corrida do desligamento: endpoints × SIGTERM

    Imagens distroless não têm sleep: use a ação nativa preStop.sleep, executada pelo kubelet. O padrão de terminationGracePeriodSeconds é 30 s e inclui o tempo do preStop.

    Referências: Termination of Pods · Container Lifecycle Hooks (sleep).

    A receita do rollout sem erro

    yaml
    spec:
  replicas: 4
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1          # um Pod a mais por vez
      maxUnavailable: 0    # capacidade nunca cai
  template:
    spec:
      terminationGracePeriodSeconds: 30
      containers:
        - name: app
          readinessProbe:  # só recebe quando pronto
            httpGet: { path: /healthz, port: 8080 }
            periodSeconds: 2
          lifecycle:
            preStop:       # espera a rede esquecer o Pod
              sleep: { seconds: 5 }
    • Estratégia: sobe o novo antes de descer o antigo.
    • Readiness: o Pod novo só entra no Service quando responde.
    • preStop: segura o SIGTERM alguns segundos.
    • Aplicação: ao receber SIGTERM, para de aceitar conexões e termina as que estão em andamento. Isso é código seu, não do Kubernetes.

    Referências: Deployments · Pod termination.

    Estratégias de deploy

    EstratégiaComoNo Kubernetes
    RollingUpdateTroca aos poucos, versões convivem por um tempoPadrão do Deployment
    RecreateDerruba tudo e sobe a nova: tem downtimestrategy.type: Recreate, para quando duas versões não podem conviver
    Blue/greenDuas versões completas; o tráfego vira de uma vezDois Deployments e troca do selector do Service ou da rota
    CanaryUma fatia do tráfego vai para a novaPesos no HTTPRoute (tópico 4.6) ou ferramentas como Argo Rollouts e Flagger

    Referências: Deployment strategy · Gateway API · traffic splitting.

    Distribuição e disrupções

    • topologySpreadConstraints: espalha as réplicas entre nós e zonas (kubernetes.io/hostname, topology.kubernetes.io/zone).
    • podAntiAffinity: impede ou evita duas réplicas no mesmo nó.
    • PodDisruptionBudget: limita quantos Pods podem sair ao mesmo tempo numa disrupção voluntária (drain, upgrade de nós, Karpenter). Não protege contra um nó que cai.
    • kubectl rollout restart reinicia com segurança, respeitando a estratégia.

    Referências: Topology Spread Constraints · Disruptions.

    disruption-controller

    Acompanha os PodDisruptionBudgets: quantos Pods ainda podem sair numa manutenção voluntária.

    • Conta os Pods saudáveis que batem com o selector do PDB.
    • Grava no status do PDB as interrupções permitidas (ALLOWED DISRUPTIONS).
    • Um kubectl drain respeita esse número.

    Referência: Specifying a Disruption Budget.

      terminal
      cat > main.go <<'EOF'
package main

import (
    "context"
    "fmt"
    "log"
    "net/http"
    "os"
    "os/signal"
    "syscall"
    "time"
)

func main() {
    host, _ := os.Hostname()
    version := os.Getenv("APP_VERSION")
    if version == "" {
        version = "v1"
    }
    mux := http.NewServeMux()
    mux.HandleFunc("/", func(w http.ResponseWriter, r *http.Request) {
        fmt.Fprintf(w, "Loja | versao=%s | host=%s\n", version, host)
    })
    mux.HandleFunc("/healthz", func(w http.ResponseWriter, r *http.Request) {
        w.Write([]byte("ok\n"))
    })
    srv := &http.Server{Addr: ":8080", Handler: mux}
    go func() {
        log.Printf("ouvindo em :8080 (versao %s)", version)
        if err := srv.ListenAndServe(); err != nil && err != http.ErrServerClosed {
            log.Fatal(err)
        }
    }()
    stop := make(chan os.Signal, 1)

    ctx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
    defer cancel()
    srv.Shutdown(ctx)
}

    Troubleshooting com kubectl debug

    Conceito
    Capítulo 10 · 3h da manhã

    O incidente num container sem shell

    Um Pod da app Go parou de responder. O plantonista tenta kubectl exec … sh e recebe um erro: a imagem distroless não tem shell, nem ps, nem curl. Foi uma escolha certa de segurança. Agora é preciso investigar sem mudar a imagem e sem reiniciar o Pod.

    Roteiro de investigação

    getSTATUS, READY, RESTARTS
    →
    describeEvents, probes, agendamento
    →
    logs--previous após um crash
    →
    exec / debuginspeção por dentro
    StatusCausa provável
    PendingSem nó com recurso, afinidade ou taint incompatível, PVC não vinculado
    ImagePullBackOffTag inexistente, registry privado sem credencial, limite de downloads
    CrashLoopBackOffA aplicação encerra ao subir: configuração, variável, dependência, liveness agressiva
    OOMKilledLimit de memória abaixo do necessário
    CreateContainerConfigErrorConfigMap ou Secret referenciado não existe
    Running, mas 0/1Readiness falhando (tópico 4.7)

    Referências: Debug Pods · Debug Running Pods.

    Por que o exec não resolve

    kubectl exec

    Roda um processo dentro do container existente, com o sistema de arquivos dele. Se a imagem não tem sh, não há o que executar.

    kubectl debug

    Adiciona ao Pod um ephemeral container com outra imagem (com shell e ferramentas), que compartilha a rede do Pod e, com --target, os processos do container alvo.

    O que não muda

    A imagem da aplicação, o Pod e o container alvo. Nada reinicia, e o IP do Pod é o mesmo.

    Referência: Ephemeral Containers · estável desde a v1.25.

    O caminho de um kubectl debug, do terminal ao runtime

    • O ephemeral container entra por um subrecurso próprio da API (pods/ephemeralcontainers), por isso não dá para adicioná-lo com kubectl edit.
    • A sessão interativa passa pelo API server até o kubelet do nó: é o mesmo caminho do exec, do logs e do port-forward.

    Referências: Ephemeral Containers · CRI · Control plane ↔ node.

    Dentro do nó: o que o container de debug enxerga

    • O Pod tem um sandbox (o processo pause) que segura os namespaces de rede, IPC e hostname. Todo container do Pod entra neles.
    • Cada container tem o seu namespace de montagem: o sistema de arquivos da própria imagem. O debugger vê o busybox, não o distroless.
    • --target=app coloca o debugger no namespace de PID do app: o ps mostra o /app.
    • O sistema de arquivos do alvo aparece em /proc/<pid>/root, se o debugger tiver permissão para inspecionar o processo.

    Referências: Share Process Namespace between Containers in a Pod · Debugging with an ephemeral container.

    Regras e variações do kubectl debug

    Ephemeral containers

    • Sem ports, probes nem resources.
    • Nunca são reiniciados e não podem ser removidos nem alterados: ficam no Pod até ele ser recriado.
    • Aparecem em spec.ephemeralContainers.
    • Não funcionam em static Pods.

    Variações

    • --copy-to=nome: cria uma cópia do Pod para depurar sem tocar no original.
    • --profile: general, baseline, restricted, netadmin, sysadmin. Sem a flag, vale o legacy, com depreciação prevista.
    • kubectl debug node/<nó>: Pod nos namespaces de rede, IPC e PID do nó, com o disco do nó em /host.

    Referências: Ephemeral Containers · Debug Running Pods.

    Versões da API e encerramento

    Conceito
    Capítulo 11 · O cluster vai mudar

    O manifesto de ontem, o cluster de amanhã

    A Loja está no ar. Mas o Kubernetes lança 3 versões por ano, e um dia o manifesto que funcionava deixa de ser aceito. Para não ser pego de surpresa no upgrade, o time aprende a perguntar ao próprio cluster quais APIs ele entende.

    Não existe uma API só

    • Toda ação no cluster é uma chamada à API, dividida em grupos com versões próprias: o Pod está em v1 (o grupo principal), o Deployment em apps/v1, o Ingress em networking.k8s.io/v1 e o HTTPRoute em gateway.networking.k8s.io/v1 (um CRD).
    • O apiVersion do manifesto precisa existir no cluster. Se não existir, o kubectl apply falha dizendo que não encontrou aquele kind naquela versão.
    • Para descobrir: kubectl api-resources (tipos e grupos), kubectl api-versions (versões servidas) e kubectl explain (os campos de um tipo).
    alphadesligada por padrão; pode sumir
    →
    betatestada; APIs beta novas vêm desligadas desde a v1.24
    →
    stable (v1)GA; mantida por muitas versões

    Referências: API Overview · API versioning · kubectl.

    Atualizar o cluster é atualizar as APIs

    Quando a API evolui, a versão antiga é marcada como depreciada e, depois, removida. Um manifesto que funcionava ontem pode falhar no cluster atualizado de hoje.

    ExemploO que mudou
    Ingress (v1.22)extensions/v1beta1 e networking.k8s.io/v1beta1 deixaram de ser servidas; use networking.k8s.io/v1. Campos também mudaram: spec.backend virou spec.defaultBackend.
    FlowSchema (v1.32)flowcontrol.apiserver.k8s.io/v1beta3 deixou de ser servida.
    kube-proxy ipvsNão é API, mas segue a mesma lógica: depreciado na v1.35, com remoção anunciada.

    Antes de atualizar um cluster, confira o guia de migração e troque os manifestos para as versões atuais. Na Aula 05, o EKS segue o mesmo calendário.

    Referência: Deprecated API Migration Guide.
