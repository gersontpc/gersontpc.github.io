    Por que precisamos de containers?

    “Na minha máquina funciona”

    Versões diferentes de linguagem, bibliotecas e SO entre o notebook do dev, homologação e produção.

    Conflito de dependências

    Duas aplicações no mesmo servidor precisando de versões diferentes da mesma biblioteca.

    Ambientes que divergem

    Servidores configurados à mão acumulam ajustes (drift) e ninguém consegue reproduzi-los.

    Entrega lenta

    Provisionar uma VM levava dias de chamado; o deploy era manual, raro e arriscado.

    Recurso ocioso

    Um servidor por aplicação, com boa parte da CPU e da memória sem uso.

    A resposta

    Empacotar a aplicação com tudo o que ela precisa num artefato único, leve e que roda igual em qualquer lugar.

    Por que foi adotado em escala

    • Experiência simples: o Docker (2013) juntou tecnologias que já existiam no kernel (namespaces, cgroups) numa experiência de três comandos: build, push, run.
    • Artefato imutável e portátil: a mesma imagem roda no notebook, no CI, no data center e em qualquer cloud.
    • Leve: sobe em segundos e ocupa MB, então dá para rodar muitas réplicas por servidor e criar ou destruir sob demanda.
    • Distribuição fácil: registries como o Docker Hub tornaram o compartilhamento de software tão simples quanto um git pull.
    • Padrão aberto: OCI (2015) e CNCF garantiram que ninguém ficasse preso a um fornecedor, e o ecossistema cresceu em torno do mesmo formato.
    • Encaixe perfeito com cloud e microsserviços: cada serviço vira um container independente, escalado e atualizado separadamente. O Kubernetes (2014) virou o padrão para orquestrar isso.

    O que os containers habilitaram no DevOps

    AmbienteDocumento de instalação e servidor configurado à mãoDockerfile versionado no Git: ambiente como código

    Container não é DevOps, mas foi o artefato comum que permitiu automatizar o caminho do commit até a produção.

    1.2

    Open Container Initiative (OCI)

    Conceito

    Um padrão aberto para containers

    Projeto da Linux Foundation criado em 2015 para garantir interoperabilidade: uma imagem criada com uma ferramenta roda em qualquer outra (Docker, Podman, containerd, CRI-O, Kubernetes, ECS, EKS).

    image-spec

    Formato da imagem: index, manifest, config e camadas, endereçados por digest SHA-256.

    github.com/opencontainers/image-spec

    runtime-spec

    Como executar um container a partir de um bundle (rootfs + config.json). Referência: runc.

    github.com/opencontainers/runtime-spec

    distribution-spec

    API HTTP de push e pull usada pelos registries (Docker Hub, ECR, GHCR, Harbor).

    github.com/opencontainers/distribution-spec

    Repositório oficial da OCI, com as três especificações e o runc: github.com/opencontainers · site: opencontainers.org

    O que a padronização trouxe

    • Portabilidade: build com Docker, execução com containerd no Kubernetes, sem conversão.
    • Liberdade de escolha: troca de ferramenta ou fornecedor sem refazer as imagens.
    • Imagens multi-plataforma: um único nome serve amd64 e arm64 (Graviton, Apple Silicon).
    • Ecossistema: scanners, assinaturas, SBOM e registries falam o mesmo formato.

    Participam da OCI empresas como Docker, Google, Microsoft, AWS, Red Hat e IBM.

    1.3

    Container runtimes

    Conceito

    O que é um container runtime?

    • Container runtime é o componente responsável por criar, iniciar e gerenciar containers no sistema operacional.
    • Executa containers de acordo com padrões, como a especificação da OCI.
    • Basicamente, pega uma imagem de container e a transforma em um processo vivo, isolado no sistema.

    Tipos de container runtime

    TipoDescriçãoExemplos
    Low-level
    baixo nível    		Só executam o container: criam, isolam e gerenciam o processo. Simples e diretos.runc, crun, runsc (gVisor)
    High-level
    alto nível    		Gerenciam o ciclo de vida completo (baixar imagem, criar, iniciar, parar, remover) e chamam um low-level para executar.containerd, CRI-O, Docker Engine
    Sandboxed
    segurança extra    		Executam containers dentro de máquinas virtuais leves para aumentar o isolamento.Kata Containers, gVisor, Firecracker

    Cada camada, um papel

    Low-level

    • Transformam uma imagem em um processo no Linux
    • Trabalham direto com cgroups e namespaces
    • Não gerenciam imagens nem clusters
    • runc: referência da OCI · crun: em C, mais leve · runsc: intercepta chamadas de sistema

    High-level

    • Baixam imagens, criam snapshots, montam redes e volumes
    • Chamam um low-level (runc) para a execução final
    • containerd: usado pelo Docker e pelo Kubernetes (CRI) · CRI-O: feito para o Kubernetes · Docker Engine: CLI + API + containerd

    Sandboxed

    • Em vez de isolar só no kernel, criam uma pequena VM por container
    • Para multi-tenant, cloud pública e setores regulados
    • Kata: microVM por container · gVisor: kernel em user-space · Firecracker: base do AWS Lambda e Fargate

    1.4

    Anatomia de uma imagem: Docker × OCI

    Conceito

    Por que o padrão OCI surgiu?

    O formato de imagem nasceu dentro do Docker e, até 2015, era definido e controlado por uma única empresa. Com concorrentes surgindo, o risco era cada ferramenta ter o seu formato.

    mar/2013Docker é lançado com formato próprio: camadas identificadas por IDs aleatórios, sem hash de conteúdo
    dez/2014CoreOS lança o rkt e a especificação appc (App Container), com outro formato de imagem (ACI)
    22/jun/2015Nasce na DockerCon, sob a Linux Foundation, o Open Container Project (depois OCI). Docker doa o formato e o runtime (libcontainer → runc). Fundadores incluem Docker, CoreOS, Google, Microsoft, Red Hat, AWS e IBM
    2016Docker 1.10 (fev) adota o Image Manifest V2, Schema 2, endereçado por conteúdo. Em abril a OCI cria a image-spec a partir do Docker v2.2. No fim do ano o appc para de evoluir
    19/jul/2017runtime-spec e image-spec 1.0
    4/mai/2021distribution-spec 1.0, baseada na Docker Registry HTTP API V2. Em mar/2024 saem as versões 1.1 de image e distribution

    O problema

    Sem padrão, cada ferramenta teria seu formato: uma imagem feita no Docker poderia não rodar no rkt, no Kubernetes ou numa cloud. O mercado ficaria preso a um fornecedor.

    A solução

    Em vez de criar algo do zero, a OCI padronizou o que já funcionava: o formato do Docker, com governança neutra e aberta para todo o ecossistema.

    Resultado

    Docker, Podman, containerd, CRI-O, Kubernetes, ECS e EKS falam o mesmo formato. Por isso uma imagem Docker e uma imagem OCI são quase idênticas.

    Fontes: anúncio da OCI (2015) · CoreOS Rocket (2014) · proposta da image-spec · appc · OCI 1.0 (2017) · distribution-spec 1.0 (2021)

    Tag × digest: endereçamento por conteúdo

    Anotação · endereçamento por conteúdo

    Cada bloco da imagem (index, manifest, config e cada camada) é identificado pelo hash SHA-256 do próprio conteúdo: o digest (sha256:3f9c…). Mesmo conteúdo gera sempre o mesmo digest; mudou um único byte, o digest é outro.

    • Integridade: no pull, o Docker recalcula o hash de cada blob e rejeita o que não bater.
    • Reaproveitamento: camadas com o mesmo digest são baixadas e armazenadas uma única vez, mesmo usadas por várias imagens.
    • Tag = ponteiro móvel: nginx:stable-alpine hoje aponta para um digest e, depois de uma atualização, para outro. Funciona como um branch no Git.
    • Digest = identidade imutável: nginx@sha256:… sempre traz exatamente os mesmos bytes. Funciona como o hash de um commit.

    Por isso, em produção, fixe a imagem pelo digest (ou use imagem:tag@sha256:…): garante que o que foi testado é o que está rodando.

    Recomendado: versão + SHA curto do commit
    v1.0.0-3123a51
    v1.0.0 versão no formato vMAJOR.MINOR.PATCH (SemVerref): diz o que mudou
    3123a51 os 7 primeiros caracteres do SHA do commit (git rev-parse --short HEAD): diz de onde veio
    • Rastreável: git show 3123a51 mostra o commit, o autor e a mudança que gerou a imagem.
    • Única e imutável: cada commit gera uma tag diferente, que nunca é reaproveitada. Com tag immutability ativo no registry, nem por engano ela é sobrescrita.
    • Simples: legível para pessoas, sem precisar copiar o digest completo.

    Em SemVer, o trecho após o hífen é um identificador de pré-release; como tags Docker não aceitam + (build metadata), o hífen é a convenção usada.

    Como emular outra arquitetura localmente?

    O host do Codespaces é amd64. Sem ajuda, o kernel dele não sabe executar um binário compilado para arm64 — e vice-versa num Mac Apple Silicon. É aí que entra o QEMU.

    O que é o QEMU

    Emulador de processador de código aberto, capaz de traduzir instruções de uma arquitetura para outra em tempo real (por exemplo, arm64 → amd64).

    binfmt_misc: a ponte com o kernel

    O Docker registra o QEMU no kernel do host via binfmt_misc. A partir daí, sempre que o kernel encontra um binário de outra arquitetura, ele encaminha a execução ao QEMU em vez de recusar — de forma transparente para o container e para quem roda o docker run.

    Emulado é compatível, não rápido: instrução por instrução traduzida custa tempo de CPU, então serve para testar e validar --platform, não para produção. Mãos à obra no exercício 1.2, parte 3.

    Exercício 1.2

    Formato Docker × formato OCI na prática

    ~30 min

    Usar docker manifest inspect para enxergar, num registry real, exatamente as peças da tabela acima: o índice multi-plataforma, o manifest de cada plataforma e as camadas. Depois, olhar por dentro da sua própria imagem para ver o mesmo formato Docker gravado em disco, e rodar localmente, via QEMU, cada uma das plataformas do índice inspecionado.

    Parte 1 · O índice multi-plataforma

    1. Peça o manifesto de uma imagem multi-plataforma do Docker Hub. Sem --verbose, o Docker resolve para a plataforma do seu host e mostra só aquele manifest:

      terminal
      docker manifest inspect nginx:stable-alpine

      Repare no mediaType do manifest (…docker.distribution.manifest.v2+json) e na lista layers, cada uma com seu próprio mediaType (…docker.image.rootfs.diff.tar.gzip) e digest.

    2. Agora peça o manifesto sem resolver a plataforma: o --verbose mostra o índice completo, com um manifest por arquitetura:

      terminal
      docker manifest inspect --verbose nginx:stable-alpine

      O conjunto dessas entradas, uma por Platform.architecture, é a manifest list — o equivalente Docker do image index da OCI. Conte quantas plataformas aparecem.

    Parte 2 · Sua imagem, o mesmo formato, gravado em disco

    1. A imagem do exercício 1.1 ainda não foi para um registry, então docker manifest inspect não a alcança — ele só lê de registries. Para ver o formato Docker local, exporte-a com docker save e liste o conteúdo do tar:

      terminal
      docker save "$IMAGE:1.0.0" -o /tmp/site.tar
tar -tvf /tmp/site.tar

      Aparecem um manifest.json, um repositories e um arquivo por camada — exatamente a linha "Em disco" da tabela para o formato Docker, sem oci-layout nem index.json.

    1.6

    Camadas e cache de build

    Conceito

    O sistema de arquivos por trás das camadas

    Union filesystem (OverlayFS)
    merged o que o container enxerga: uma árvore única
    ↑ sobreposição
    upperdir camada de escrita do container · copy-on-write
    lowerdir 3 COPY index.html · somente leitura
    lowerdir 2 RUN apk add … · somente leitura
    lowerdir 1 FROM alpine · somente leitura
    • O kernel empilha as camadas da imagem (lowerdir) e uma camada gravável (upperdir) e mostra ao container uma visão única (merged).
    • Copy-on-write: ao alterar um arquivo de uma camada inferior, ele é copiado para a upperdir antes da escrita. A imagem nunca muda.
    • Apagar um arquivo cria um whiteout na camada de cima: ele some da visão, mas continua ocupando espaço na camada de baixo.
    • Várias imagens e containers compartilham as mesmas camadas em disco.
    Backend de armazenamentoSituação
    containerd image store (snapshotter overlayfs)Padrão em instalações novas desde o Docker Engine 29 (nov/2025). É o mesmo mecanismo do containerd no Kubernetes e suporta imagens multi-plataforma e attestations nativamente
    overlay2Driver clássico, padrão por anos e ainda o mais compatível. Continua em uso em instalações atualizadas de versões anteriores
    fuse-overlayfs, btrfs, zfs, vfsCasos específicos: rootless em kernel antigo, sistemas de arquivos avançados, testes
    aufs, devicemapper, overlayLegados, removidos das versões atuais

    Descubra o seu com docker info (linhas Storage Driver e driver-type). Fonte: Docker docs · Select a storage driver e Docker Engine v29.

    Cada instrução, uma camada

    Container: camada de escrita efêmera · copy-on-write
    CMD ["nginx","-g","daemon off;"] só metadado, 0 B
    COPY index.html /usr/share/nginx/html/ camada
    RUN apk add --no-cache curl camada
    FROM nginx:stable-alpine camadas da base
    • RUN, COPY e ADD criam camadas. ENV, CMD, EXPOSE e LABEL só alteram a configuração.
    • As camadas são somente leitura e compartilhadas entre imagens e containers (union filesystem, overlay2).
    • Apagar um arquivo numa camada posterior não reduz a imagem: ele continua na camada anterior.

    Menos camadas não é o único critério: o que mais pesa é o que fica dentro delas (cache do apt, arquivos temporários) e a ordem, que define o reaproveitamento do cache.

    Cache: do que muda menos para o que muda mais

    O build compara cada instrução com a do cache. Na primeira camada que mudar (ou cuja anterior já tenha mudado), o Docker para de reaproveitar e reconstrói dali para cima, na ordem do Dockerfile.

    Ruim: COPY . . antes de instalar

    Dockerfile

CMD ["node","server.js"]
    CMD
    RUN npm installreinstala tudo de novo
    COPY . .muda a cada commit
    FROM node:20-alpinecache

    Bom: manifesto antes do código

    Dockerfile
    FROM node:20-alpine
COPY package.json package-lock.json ./
RUN npm install
COPY . .
CMD ["node","server.js"]
    CMD
    COPY . .muda sempre, mas é rápida
    RUN npm installcache hit — pulado
    COPY package*.jsonsó muda com o manifesto
    FROM node:20-alpinecache

    Nos dois casos o COPY . . muda a cada commit — a diferença é o que está abaixo dele na pilha. No Bom, o npm install já rodou antes de copiar o código e continua em cache; no Ruim, ele é uma camada acima do código e é refeito toda vez.

    SBOM: a lista de ingredientes da imagem

    Software Bill of Materials é o inventário de tudo o que compõe um artefato: pacotes do SO, bibliotecas da aplicação, versões, licenças e origem. Como o rótulo de um alimento, diz exatamente o que tem dentro.

    Para que serve

    • Saiu uma CVE nova: descobrir em minutos quais imagens usam a versão afetada
    • Auditoria e compliance de licenças
    • Exigido por regulações e contratos (governo dos EUA, setor financeiro)

    Formatos

    • SPDX (Linux Foundation, padrão ISO/IEC 5962)
    • CycloneDX (OWASP)
    • Ambos em JSON, anexáveis à imagem no registry como artefato OCI

    Como gerar

    • trivy image --format cyclonedx
    • syft <imagem>
    • docker buildx build --sbom=true (atestado no push)
    • docker scout sbom (substitui o antigo docker sbom)

    Multi-stage e distroless

    Conceito

    Separar o que constrói do que executa

    O multi-stage divide a construção em etapas independentes no mesmo Dockerfile. No final, só os artefatos necessários são copiados para a imagem de produção.

    Menor

    Compiladores, SDKs e bibliotecas de desenvolvimento ficam fora da imagem final.

    Mais segura

    Sem ferramentas de build nem arquivos temporários ou sensíveis na imagem publicada.

    Build mais rápido

    Etapas independentes rodam em paralelo e aproveitam cache.

    Como funciona

    Etapa 1: buildFROM golang:1.25-alpine AS build · compila o binário
    →
    COPY --from=buildcopia só o artefato
    →
    Etapa 2: produçãoFROM distroless/static · binário + usuário nonroot
    • Cada FROM inicia uma etapa; AS nome permite referenciá-la.
    • docker build --target build para parar numa etapa (útil para testes).
    • Vale para qualquer linguagem: pip install --user numa etapa e cópia de /root/.local na outra, npm ci + cópia do dist/, mvn package + cópia do .jar.

    Distroless

    Imagens que contêm apenas a aplicação e suas dependências de runtime: sem shell, sem gerenciador de pacotes, sem utilitários como curl, wget ou netcat. Se um componente não está lá, ele não pode ser explorado.

    Opções

    • Google distroless (gcr.io/distroless/*)
    • Chainguard / Wolfi
    • Construção própria com apko + melange, sem Dockerfile

    gersontpc/image-base

    • Java, Python, Go, Node.js e .NET, amd64 e arm64
    • Camada única, non-root, SBOM a cada build
    • Trivy barra CVEs HIGH/CRITICAL antes do push

    Benefícios observados na pesquisa: menos CVEs, pull mais rápido e redução de custo de 20% a 30%. Sem shell, a depuração usa ephemeral containers (Aula 04).

    Tags, versionamento e registry

    Conceito

    Anatomia de uma referência

    docker.io/usuario/container-technologies:1.4.2

    Registry

    Docker Hub (padrão), Amazon ECR, GHCR, Harbor, Artifact Registry, ACR.

    Repositório

    Usuário ou organização + nome da aplicação.

    Tag × digest

    Tag é legível e mutável. Digest (@sha256:…) é imutável.

    Boas práticas de tag

    TagUso
    1.4.2Versão exata (SemVer). É o que vai para produção
    1.4 / 1Ponteiros para a última correção da série, úteis para consumidores
    v1.4.2-3f9c2abRecomendado: versão + SHA curto do commit. Legível, rastreável até o autor e nunca reaproveitada
    sha-3f9c2abCommit que gerou a imagem: rastreabilidade do código ao container
    stable + 010726-0152Canal móvel + referência imutável por data (padrão do image-base)
    latestEvite em produção: não diz qual versão está rodando nem permite rollback confiável
    • Build once, deploy many: a mesma imagem (mesmo digest) é promovida de dev para produção.
    • Ative tag immutability no registry (o ECR suporta) para impedir sobrescrita.
    • Autentique com token de acesso, nunca com a senha da conta.

    SemVer + Conventional Commits

    Semantic Versioning

    MAJOR.MINOR.PATCH

    • MAJOR: mudança incompatível
    • MINOR: funcionalidade compatível
    • PATCH: correção compatível
    • Pré-release: 2.0.0-rc.1

    Conventional Commits

    • fix: corrige timeout → PATCH
    • feat: adiciona /healthz → MINOR
    • feat!: remove API v1 ou BREAKING CHANGE: → MAJOR
    • chore:, docs:, ci: não geram versão

    Com commits semânticos, ferramentas como semantic-release e release-please calculam a próxima versão e a tag da imagem automaticamente no pipeline.

      Sinais do Linux

      Sinais são o mecanismo que o kernel usa para notificar processos sobre eventos.

      SIGTERM (15)Pede que o processo termine de forma graciosa
      SIGKILL (9)Força a terminação imediata; não pode ser ignorado
      SIGINT (2)Interrompe o processo (Ctrl+C)
      SIGQUIT (3)Como o SIGINT, mas gera dump de memória
      SIGHUP (1)Hangup; usado para recarregar configuração
      SIGSTOP (19)Suspende a execução (docker pause usa o freezer do cgroup para o mesmo efeito)
      SIGCONT (18)Retoma um processo suspenso

      Ciclo de vida e sinais

      created
      →
      running
      →
      paused
      →
      exited
      →
      removed
      • docker stop envia SIGTERM ao PID 1 e, após 10 s, SIGKILL.
      • A aplicação precisa tratar SIGTERM para desligar de forma graciosa.
      • Na forma shell do CMD, o PID 1 é o sh, que não repassa o sinal. Use a forma exec ou --init.

      Hipótese Containers na bridge padrão se falam pelo IP, mas não pelo nome, e só são acessados do host com -p.

        terminal

docker run -d --name a2 alpine:3.22 sleep 3600
docker network ls
docker inspect -f '{{.NetworkSettings.IPAddress}}' a1 a2

        terminal

docker exec a1 ping -c2 a2

        terminal
        docker exec a1 ping -c2 8.8.8.8
docker run -d --name w1 nginx:stable-alpine

      Ping pelo IP e para 8.8.8.8 respondem; pelo nome dá ping: bad address 'a2'. O nginx só responde no host depois do -p 8080:80 (HTTP/1.1 200 OK).

      Parte 2 · bridge personalizada

      Hipótese Numa rede criada pelo usuário, o Docker oferece DNS interno e isola os containers de outras redes.

      1. Crie uma rede e suba dois containers nela:

        terminal
        docker network create lab-net
docker run -d --name b1 --network lab-net alpine:3.22 sleep 3600
docker run -d --name b2 --network lab-net alpine:3.22 sleep 3600

      2. Teste a resolução de nomes e veja quem responde o DNS:

        terminal
        docker exec b1 ping -c2 b2
docker exec b1 nslookup b2
docker exec b1 cat /etc/resolv.conf

      3. Teste o isolamento entre redes e depois conecte a1 à lab-net:

        terminal
        docker exec a1 ping -c2 -W2 $(docker inspect -f '{{(index .NetworkSettings.Networks "lab-net").IPAddress}}' b1) || echo "isolado"
docker network connect lab-net a1
docker exec a1 ping -c2 b1
      Resultado esperado

      Ping pelo nome funciona e o resolv.conf aponta para nameserver 127.0.0.11 (DNS embutido do Docker). a1 não alcança b1 até ser conectado à lab-net; depois, resolve até pelo nome.

      Parte 3 · host

      Hipótese Com --network host o container usa a pilha de rede do host: sem isolamento e sem NAT.

      1. Rode um nginx na rede do host, sem -p, e acesse direto:

        terminal
        docker run -d --name h1 --network host nginx:stable-alpine
sleep 1; curl -sI localhost:80 | head -1

      2. Compare as interfaces que o container enxerga com as do host:

        terminal
        docker run --rm --network host alpine:3.22 ip -brief addr
ip -brief addr
      Resultado esperado

      O curl na porta 80 responde sem nenhum -p, e o container lista as mesmas interfaces do codespace (eth0, docker0, veth…).

      Parte 4 · none

      Hipótese Com --network none o container fica totalmente isolado: só existe o loopback.

      1. Rode um container sem rede e tente sair:

        terminal
        docker run --rm --network none alpine:3.22 ip -brief addr
docker run --rm --network none alpine:3.22 ping -c2 -W2 8.8.8.8
      Resultado esperado

      Só aparece a interface lo, e o ping falha com Network unreachable.

      1. Remova os containers e a rede:

        terminal
        docker rm -f a1 a2 b1 b2 w1 h1

      Hipótese A camada de escrita pertence ao container: os dados sobrevivem a stop/restart, mas somem quando o container é removido.

      1. Grave um arquivo dentro do container, pare, suba de novo e depois recrie:

        terminal
        docker run -d --name c1 alpine:3.22 sleep 3600

docker exec c1 cat /tmp/arquivo.txt; docker rm -f c1
      Resultado esperado

      Depois do restart o arquivo continua lá; no container recriado, cat falha com No such file or directory.

      Parte 2 · volume nomeado

      Hipótese Um volume vive fora do ciclo de vida do container e é gerenciado pelo Docker: pode ser usado por vários containers.

      1. Crie um volume e grave nele com um container descartável:

        terminal
        docker volume create dados
docker run --rm -v dados:/data alpine:3.22 sh -c 'echo "gravado em $(date)" >> /data/log.txt'

      2. Leia com outro container e grave de novo:

        terminal
        docker run --rm -v dados:/data alpine:3.22 sh -c 'echo "gravado em $(date)" >> /data/log.txt; cat /data/log.txt'

      3. Veja onde o Docker guarda o volume:

        terminal
        docker volume ls
docker volume inspect dados --format '{{.Mountpoint}}'
      Resultado esperado

      log.txt mostra duas linhas, gravadas por containers diferentes que já foram removidos. O volume fica em /var/lib/docker/volumes/dados/_data.

      Parte 3 · bind mount

      Hipótese Bind mount liga uma pasta do host ao container: o que muda de um lado aparece do outro, e os arquivos são do host.

      1. Crie uma pasta no host e sirva-a com o nginx, somente leitura (:ro):

        terminal
        mkdir -p ~/labs/bind && echo '<h1>v1 via bind mount</h1>' > ~/labs/bind/index.html
docker run -d --name bind -p 8082:80 -v ~/labs/bind:/usr/share/nginx/html:ro nginx:stable-alpine
sleep 1; curl -s localhost:8082

      2. Edite o arquivo no host e acesse de novo, sem reiniciar nada:

        terminal
        echo '<h1>v2 editado no host</h1>' > ~/labs/bind/index.html
curl -s localhost:8082

      3. Tente escrever pelo container e remova-o; o arquivo continua no host:

        terminal
        docker exec bind sh -c 'echo teste > /usr/share/nginx/html/x.html'
docker rm -f bind
ls ~/labs/bind
      Resultado esperado

      O segundo curl já mostra “v2 editado no host”. A escrita pelo container falha com Read-only file system, e index.html continua no host depois do rm.

        terminal
        docker restart tmp
docker exec tmp ls /cache
docker rm -f tmp
      Resultado esperado

      df mostra /cache como tmpfs de 16 MB; depois do restart, a pasta está vazia.

      Docker Compose

      Conceito

      A aplicação descrita em um arquivo

      Docker Compose define serviços, redes e volumes de forma declarativa em compose.yaml. Um comando sobe o ambiente inteiro, igual para todo o time.

      services

      Cada container: image ou build, ports, environment, volumes, depends_on, healthcheck, restart.

      volumes

      Volumes nomeados, criados com o prefixo do projeto.

      networks

      Por padrão, uma rede <projeto>_default com DNS pelo nome do serviço.

      O campo version: é obsoleto na Compose Specification e gera aviso. Use docker compose (v2, plugin) em vez de docker-compose (v1, descontinuado).

      Comandos do dia a dia

      docker compose up -dCria e sobe tudo em segundo plano
      docker compose psEstado e saúde dos serviços
      docker compose logs -f wordpressAcompanha os logs de um serviço
      docker compose exec db shShell num serviço em execução
      docker compose configValida e mostra o YAML final (com variáveis resolvidas)
      docker compose down / down -vRemove containers e redes / também os volumes

      Ordem de inicialização com healthcheck

      depends_on simples só espera o container iniciar, não ficar pronto. Com condition: service_healthy, o WordPress só sobe depois que o banco responde ao healthcheck.

      restart: no · always · on-failure · unless-stopped.

      No Kubernetes, o equivalente é a readinessProbe, e a aplicação deve tolerar dependências indisponíveis com retry.

      Limites de recursos no Compose

      yaml
      services:
  api:
    image: minha/api:v1
    deploy:
      replicas: 3
      resources:
        limits:   { cpus: "0.50", memory: 256M }
        reservations: { memory: 128M }
      • Sem limite, um container pode consumir toda a CPU e memória do host e derrubar os vizinhos.
      • Escalar funciona para serviços stateless. Não escale um banco com --scale: cada réplica teria seus próprios dados.
      • Serviços com ports: "8080:80" fixo não escalam no mesmo host (conflito de porta).

      Por que orquestrar e Docker Swarm

      Conceito

      O que um orquestrador faz

      Estado desejado“3 réplicas de web:v2”
      →
      Observaestado atual do cluster
      →
      Comparadiferença entre os dois
      →
      Agecria, remove, move containers
      • Scheduling: decide em qual nó cada container roda.
      • Auto-reparo: container ou nó caiu, a réplica volta em outro lugar.
      • Rolling update e rollback, service discovery e balanceamento.

      Arquitetura do Docker Swarm

      Managers

      Guardam o estado do cluster e reconciliam o desejado com o real. Replicados via Raft: precisam de quórum (N/2 + 1). 3 managers toleram 1 falha; 5 toleram 2.

      Workers

      Executam as tasks (containers) de cada service.

      Rede

      2377/tcp gerência · 7946/tcp+udp descoberta · 4789/udp overlay (VXLAN). Routing mesh publica a porta em todos os nós.

      Nativo no Docker, simples e com o mesmo formato do Compose (docker stack deploy). O mercado, porém, padronizou no Kubernetes. Portainer oferece uma interface gráfica para Swarm.

      Prática
      Exercício 2.6

      Swarm de um nó: auto-reparo e rolling update

      ~25 min

      1. Inicie o Swarm e crie um service com 3 réplicas:

        terminal

        terminal

        terminal
        docker service scale web=5

    image: traefik/whoami

      replicas: 3

for i in $(seq 6); do curl -s localhost:8084 | grep Hostname; done

        terminal
        docker stack rm demo; docker service rm web; docker swarm leave --force

        ECS: operando o service

        Conceito

        O service como orquestrador

        Auto-reparo

        Se uma task para ou falha no health check, o service sobe outra para manter o desiredCount.

        Escala

        Mude o desiredCount na mão ou use Service Auto Scaling por CPU, memória ou requisições por alvo do ALB.

        O papel de cada componente

        Control plane

        • kube-apiserver: porta de entrada. Tudo passa pela API (kubectl, controllers, kubelet).

        • container runtime: containerd ou CRI-O, via CRI.
        • kube-proxy (opcional): regras de rede (iptables/IPVS/nftables) para os Services. Alguns CNIs, como o Cilium, o substituem.

        Addons

        • DNS: CoreDNS dá nome aos Services (web.app.svc.cluster.local).
        • Rede dos Pods (CNI): Flannel, Calico, Cilium, VPC CNI na AWS.
        • Métricas: metrics-server alimenta kubectl top e o HPA.
        • Logging e Dashboard: opcionais.

          4.1

          Health checks: probes

          Conceito

          Três perguntas diferentes

          ProbePerguntaSe falhar
          startupProbeA aplicação terminou de iniciar?Segura as outras probes; após o limite, reinicia o container
          readinessProbePode receber tráfego agora?Pod sai dos endpoints do Service (não reinicia)
          livenessProbeEstá vivo ou travado?kubelet reinicia o container

          Tipos: httpGet, tcpSocket, grpc, exec. Parâmetros: initialDelaySeconds, periodSeconds, timeoutSeconds, failureThreshold.

          Armadilhas comuns

          • Liveness que depende do banco: o banco cai e todos os Pods reiniciam em cascata. Liveness deve checar só o próprio processo.
          • Liveness sem startupProbe em apps lentas (JVM): o Pod é morto antes de subir e entra em CrashLoopBackOff.
          • Readiness igual à liveness: perde-se a chance de tirar o Pod do tráfego sem reiniciá-lo.
          • Exponha endpoints dedicados: /healthz (liveness) e /ready (readiness), como o Spring Actuator faz.

          4.2

          Recursos e autoescala

          Conceito

          Requests e limits

          requests

          Reserva usada pelo scheduler para escolher o nó. Base do cálculo de % do HPA.

          limits

          Teto aplicado pelo kernel (cgroups). CPU acima do limite: throttling. Memória acima: OOMKilled.

          QoS class

          Guaranteed (requests = limits), Burstable, BestEffort (nada definido, primeiro a ser despejado).

          Como definir? Meça: kubectl top, métricas de observabilidade e as recomendações do VPA (modo Off). Muitas equipes usam limit de memória e dispensam limit de CPU para evitar throttling.

          Três camadas de escala

          MecanismoEscalaCom base em
          HPANúmero de PodsCPU/memória, métricas custom (req/s, fila) ou externas
          VPARequests de cada PodHistórico de consumo
          KEDAPods, inclusive até zeroEventos: SQS, Kafka, Prometheus, cron
          Cluster Autoscaler / KarpenterNúmero de nósPods pendentes por falta de recurso

          CPU e memória nem sempre refletem carga real. Para APIs, requisições por segundo ou latência costumam ser sinais melhores.

          4.3

          Deploy sem downtime

          Conceito

          Estratégia de RollingUpdate

          maxSurge

          Quantos Pods a mais podem existir durante o rollout (número ou %). Maior = mais rápido, mais recurso.

          maxUnavailable

          Quantos Pods podem ficar indisponíveis. 0 = capacidade nunca cai abaixo do desejado.

          Com readiness correta, o Pod novo só recebe tráfego quando está pronto e o antigo só sai depois. Alternativas: Recreate, blue/green e canary (Argo Rollouts, Flagger).

          Desligamento gracioso do Pod

          Pod marcado Terminatingsai dos endpoints
          →
          preStopespera o LB/kube-proxy propagar
          →
          SIGTERMapp fecha conexões
          →
          SIGKILLapós terminationGracePeriodSeconds (30 s)

          A remoção dos endpoints e o SIGTERM acontecem em paralelo. Um preStop curto evita que requisições em trânsito cheguem a um processo já encerrando. Em imagens distroless (sem sleep), use a ação nativa preStop.sleep.

          Distribuição e disrupções

          • nodeSelector / nodeAffinity: segmente workloads por grupo de nós (ex.: role: app, spot × on-demand).
          • podAntiAffinity / topologySpreadConstraints: espalhe réplicas entre nós e zonas de disponibilidade.
          • PodDisruptionBudget: limita quantos Pods podem sair ao mesmo tempo em manutenções (drain, upgrade de nós, Karpenter).
          • Rollout também serve para reiniciar com segurança: kubectl rollout restart deployment/app.

          Amazon EKS e boas práticas

          Conceito

          Kubernetes gerenciado: quem cuida de quê

          AWS

          • Control plane (API server, etcd) em 3 AZs
          • Endpoint exposto por NLB, público ou privado
          • Patches e upgrades do control plane
          • SLA de 99,95%

          Você

          • Data plane (nós), exceto Fargate e Auto Mode
          • Add-ons: VPC CNI, CoreDNS, kube-proxy, EBS CSI, AWS Load Balancer Controller
          • Workloads, RBAC, rede, segurança
          • Iniciar os upgrades de versão

          Equivalentes: GKE (Google Cloud) e AKS (Azure).

          Opções de data plane e escala de nós

          OpçãoNósQuando
          Managed node groupsEC2 em ASG, com ciclo de vida gerenciadoPadrão para a maioria
          Self-managed nodesEC2 e ASG seusAMIs e bootstrap customizados
          FargateServerless, 1 Pod = 1 micro-VMCargas pequenas e isoladas (sem DaemonSet)
          EKS Auto ModeAWS provisiona e opera os nós (baseado em Karpenter)Menos operação de cluster

          Cluster Autoscaler ajusta ASGs de tipos fixos. Karpenter cria a instância certa para os Pods pendentes, usa spot e consolida nós ociosos.

          Workflow de criação

          ClusterVPC, subnets, IAM
          →
          Node groupsou Auto Mode / Karpenter
          →
          Add-onsCNI, DNS, CSI, LB Controller
          →
          Workloadsvia CI/CD ou GitOps

          Ferramentas: eksctl, Terraform (módulo terraform-aws-modules/eks, EKS Blueprints), CloudFormation, CDK, console e AWS CLI.

          Acesso: access entries no lugar do ConfigMap aws-auth; EKS Pod Identity (ou IRSA) para dar permissões AWS a cada ServiceAccount com mínimo privilégio.

          Práticas recomendadas

          Infra como código

          Terraform/CloudFormation + GitOps (Argo CD, Flux). Nada manual no console: evita drift.

          Upgrades

          Uma minor por vez, leia o changelog e APIs removidas, backup com Velero, comece por dev/staging, considere blue/green de cluster. Acompanhe o calendário de suporte do EKS.

          Segurança

          Endpoint privado, security groups, hardening de AMI (CIS, Bottlerocket), imagens escaneadas, Pod Security Standards.

          Dimensionamento

          Requests calibrados (VPA), ec2-instance-selector, Kubernetes Instance Calculator e limite de Pods por nó (IPs do VPC CNI).

          Referências: AWS Well-Architected Framework e EKS Best Practices Guide.

          Da app local ao EKS com eksctl

          ~50 min · opcional

          Provisionar um cluster EKS declarado em YAML, publicar a app Go com um Service LoadBalancer e destruir tudo ao final. Roteiro detalhado em containers/Lab-04/02-cluster-eks.

          Custo

          Requer conta AWS. O EKS cobra por hora de control plane, além das instâncias EC2 e do load balancer. Execute o passo de limpeza no mesmo dia.

          1. Configure as credenciais (de preferência como Codespaces secrets AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY e AWS_DEFAULT_REGION) e valide:

            terminal
            # AWS CLI e eksctl (se ainda não estiverem instalados)
curl -s "https://awscli.amazonaws.com/awscli-exe-linux-x86_64.zip" -o awscliv2.zip && unzip -q awscliv2.zip && sudo ./aws/install && rm -rf aws awscliv2.zip
curl -sL "https://github.com/eksctl-io/eksctl/releases/latest/download/eksctl_Linux_amd64.tar.gz" | tar -xz -C /tmp && sudo mv /tmp/eksctl /usr/local/bin

aws sts get-caller-identity
eksctl version

          2. Publique a imagem Go no Docker Hub para o EKS conseguir baixá-la:

            terminal
            cd ~/labs/app-go
docker tag app-go:v1 "$DOCKERHUB_USER/app-go:v1" && docker push "$DOCKERHUB_USER/app-go:v1"

          3. Declare e crie o cluster (15 a 20 minutos):

            terminal
            mkdir -p ~/labs/eks && cd ~/labs/eks
cat > cluster.yaml <<'EOF'
apiVersion: eksctl.io/v1alpha5
kind: ClusterConfig
metadata:
  name: demo-eks
  region: us-east-1
  # sem "version": usa a versão padrão atual do EKS
managedNodeGroups:
  - name: ng-app
    instanceType: t3.medium
    minSize: 2
    desiredCapacity: 2
    maxSize: 4
    labels: { role: app }
addons:
  - name: vpc-cni
  - name: coredns
  - name: kube-proxy
  - name: eks-pod-identity-agent
EOF
eksctl create cluster -f cluster.yaml
kubectl get nodes -L role,topology.kubernetes.io/zone

          4. Reaproveite o manifesto da 4.3 trocando a imagem e exponha com LoadBalancer:

            terminal
            sed -e "s#image: app-go:v1#image: $DOCKERHUB_USER/app-go:v1#" ~/labs/prod/app-go.yaml > app-go.yaml
kubectl apply -f app-go.yaml
kubectl expose deployment app-go --name app-go-lb --type LoadBalancer --port 80 --target-port 8080
kubectl get svc app-go-lb -w      # aguarde o EXTERNAL-IP (hostname do ELB) e Ctrl+C
curl -s http://$(kubectl get svc app-go-lb -o jsonpath='{.status.loadBalancer.ingress[0].hostname}')

          5. Destrua tudo:

            terminal
            kubectl delete svc app-go-lb
eksctl delete cluster -f cluster.yaml --wait
          Resultado esperado
          • 2 nós Ready em zonas de disponibilidade diferentes, com o label role=app.
          • Os mesmos manifestos do k3d funcionam no EKS (o Ingress com Traefik fica sem controller e pode ser ignorado).
          • O curl no hostname do ELB responde versao=v1; ao final não resta nenhum recurso na conta.
