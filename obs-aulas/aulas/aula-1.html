Tópicos
    1.1

    Onde tudo começou: de SysAdmin a Platform Engineering

    Conceito
    Capítulo 1 · A evolução

    Do trabalho manual à experiência do desenvolvedor

    Antes, um time escrevia o código e outro o colocava no ar. Quem operava não sabia o que tinha mudado; quem desenvolvia não sabia como o sistema se comportava em produção. A observabilidade nasce dessa distância.

    A evolução

    System Admintrabalho manual: servidores configurados à mão
    →
    DevOpsautomação: pipelines e infraestrutura como código
    →
    SREconfiabilidade: SLOs, error budget, golden signals
    →
    Platform Engineeringexperiência do desenvolvedor: plataforma self-service

    DevOps

    DevOps é uma cultura, metodologia e conjunto de práticas que unem desenvolvimento (Dev) e operações (Ops) para automatizar e integrar processos, com foco em entrega contínua, qualidade e colaboração.

    O problema: silos

    • Dev quer mudar rápido; Ops quer estabilidade
    • O “muro da confusão” entre os dois times
    • Culpa em vez de aprendizado

    A proposta

    • Quebrar os silos: times com responsabilidade de ponta a ponta
    • “You build it, you run it”
    • Feedback rápido da produção para o desenvolvimento

    Referências: Gartner · DevOps.

    Os pilares do DevOps

    PilarO que faz
    Controle de versãoMantém versões do código e permite colaborar
    Integração contínuaCompila, valida, revisa e testa a cada mudança
    Entrega contínuaCommits frequentes, entregas menores e mais seguras
    Implantação contínuaDeploy automático em produção, com menos risco
    Monitoramento contínuoFecha o ciclo: mostra como cada mudança se comporta em produção
    Negócio“DevOps, em certo sentido, é sobre a criação de uma fábrica de entrega de valor: um pipeline simplificado e sem desperdício, por meio do qual o valor pode ser entregue ao negócio com um tempo de ciclo previsivelmente rápido.” — Mark Schwartz, The Art of Business Value

    Platform Engineering

    A Engenharia de Plataforma constrói ferramentas, infraestrutura e serviços que dão suporte aos times de desenvolvimento, para que eles se concentrem em entregar valor ao cliente.

    • Observabilidade vira um produto da plataforma: o time cria um serviço e já ganha métricas, logs, traces e dashboards padrão.
    • OpenTelemetry é a peça que permite esse padrão sem amarrar a empresa a um fornecedor.

    Referências: Platform Tooling Landscape · CNCF Landscape · Observability.

"""API da Loja instrumentada com OpenTelemetry. As métricas ficam em :9464/metrics para o Prometheus."""
import asyncio, random
from fastapi import FastAPI, HTTPException
from opentelemetry import metrics
from opentelemetry.sdk.metrics import MeterProvider
from opentelemetry.sdk.resources import Resource
from opentelemetry.exporter.prometheus import PrometheusMetricReader
from opentelemetry.instrumentation.fastapi import FastAPIInstrumentor
from opentelemetry.instrumentation.system_metrics import SystemMetricsInstrumentor
from prometheus_client import start_http_server

# 1. Provider de métricas: o leitor Prometheus expõe tudo em /metrics (porta 9464)
start_http_server(9464)
metrics.set_meter_provider(MeterProvider(
    resource=Resource.create({"service.name": "loja-api", "service.version": "1.0.0"}),
    metric_readers=[PrometheusMetricReader()]))

# 2. Instrumentação automática: duração e requisições HTTP, CPU e memória do processo
app = FastAPI(title="Loja API")
FastAPIInstrumentor.instrument_app(app)
SystemMetricsInstrumentor(config={"process.cpu.utilization": None, "process.memory.usage": None}).instrument()

# 3. Métrica de negócio criada à mão
meter = metrics.get_meter("loja.api")
pedidos = meter.create_counter("loja.pedidos", unit="{pedido}", description="Pedidos finalizados")

# Chaos: latência extra e taxa de erro ajustáveis em tempo de execução
chaos = {"latencia": 0.0, "erro": 0.0}
PRODUTOS = {1: "Camiseta", 2: "Caneca", 3: "Mochila", 4: "Boné"}


async def simular(base):
    await asyncio.sleep(random.uniform(*base) + chaos["latencia"])
    if random.random() < chaos["erro"]:
        raise HTTPException(500, "falha simulada")


@app.get("/produtos")
async def listar():
    await simular((0.01, 0.05))
    return PRODUTOS


@app.get("/produtos/{pid}")
async def detalhar(pid: int):
    await simular((0.01, 0.08))
    if pid not in PRODUTOS:
        raise HTTPException(404, "produto não encontrado")
    return {"id": pid, "nome": PRODUTOS[pid]}


@app.post("/checkout")
async def checkout():
    await simular((0.1, 0.6))
    if random.random() < 0.02:
        raise HTTPException(503, "gateway de pagamento indisponível")
    pedidos.add(1, {"pagamento": random.choice(["pix", "cartao"])})
    return {"status": "aprovado"}


@app.get("/relatorio")
def relatorio():
    # Rota pesada de CPU: usada para provocar saturação
    total = sum(i * i for i in range(2_000_000))
    return {"linhas": total % 1000}


@app.get("/health")
async def health():
    return {"status": "ok"}


@app.post("/chaos")
async def ajustar_chaos(latencia: float = 0.0, erro: float = 0.0):
    chaos.update(latencia=latencia, erro=erro)
    return chaos
EOF

    1.2

    SRE: confiabilidade como engenharia

    Conceito
    Capítulo 2 · Google, 2003

    E se a operação fosse feita por engenheiros de software?

    O SRE (Site Reliability Engineering) surgiu no Google em 2003 para escalar a confiabilidade dos serviços: automatizar tarefas manuais, operar com código e equilibrar velocidade de inovação com estabilidade.

    O que é SRE

    SRE é uma prática que aplica princípios de engenharia de software às operações de TI. O objetivo é garantir que os sistemas sejam confiáveis, escaláveis e eficientes, usando observabilidade para melhorar continuamente.

    Princípios

    • Confiabilidade é a funcionalidade mais importante
    • 100% é a meta errada
    • Reduzir trabalho manual repetitivo (toil)

    Práticas

    • SLOs e error budget
    • Golden signals
    • Postmortems sem culpados

    Referências: Google · SRE books.

    Níveis de serviço: SLA, SLO, SLI

    ConceitoO que éExemplo
    SLIMétrica que mede o desempenho do serviço% de requisições com sucesso e abaixo de 300 ms
    SLOMeta interna para o SLI99,95% de disponibilidade no mês
    SLACompromisso com o cliente, com compensação99,9% de disponibilidade, ou crédito na fatura
    Error budgetMargem de erro permitida: 100% − SLOSLO de 99,95% → 0,05% ≈ 21,6 min por mês
    Burn rateVelocidade de consumo do error budgetBurn rate 2 → orçamento acaba na metade do mês

    O error budget equilibra estabilidade e velocidade: com orçamento sobrando, o time arrisca mais; com orçamento no fim, prioriza confiabilidade.

    Os 4 golden signals

    SinalPerguntaComo medir
    LatênciaQuanto tempo leva para responder?Percentis (p50, p95, p99), separando sucesso de erro
    TráfegoQuanta demanda o sistema recebe?Requisições por segundo (RPS), throughput
    ErrosQuantas requisições falham?Taxa de 5xx, timeouts, respostas erradas
    SaturaçãoQuão perto do limite o sistema está?CPU, memória, I/O, filas, requisições em andamento

    Criados no SRE do Google para detectar rápido o que afeta o usuário. Se você só puder medir quatro coisas, meça estas.

    Referências: Google SRE Book · Monitoring Distributed Systems.

    Outros métodos: RED e USE

    RED (serviços)

    • Rate: requisições por segundo
    • Errors: requisições com falha
    • Duration: distribuição da latência

    USE (recursos)

    • Utilization: % do tempo ocupado
    • Saturation: trabalho na fila
    • Errors: falhas do recurso

    Quando usar

    • RED para APIs e microsserviços
    • USE para CPU, disco, rede, pools
    • Golden signals cobrem os dois

    Referências: The RED Method · The USE Method.

    Observabilidade e OpenTelemetry

    Conceito
    Capítulo 3 · Saber o que está acontecendo

    Monitorar responde “está funcionando?”. Observar responde “por quê?”

    Com microsserviços, nuvem e, agora, modelos de IA, as falhas deixaram de ser previsíveis. Não dá para criar um painel para cada pergunta: é preciso dados ricos para responder perguntas novas.

    Monitoramento × observabilidade

    MonitoramentoObservabilidade
    PerguntaEstá funcionando?Por que está se comportando assim?
    AbordagemVerificações e painéis para falhas conhecidasExplorar dados para entender falhas novas
    SinaisMétricas agregadas, health checksMétricas, logs e traces correlacionados

    Referências: Observability primer.

    Os pilares

    Métricas

    • Números agregados no tempo
    • Baratas, ótimas para tendência e alerta
    • Foco desta aula

    Logs

    • Eventos com texto e contexto
    • Detalhe do que aconteceu

    Traces

    • O caminho de uma requisição entre serviços
    • Onde o tempo foi gasto

    OpenTelemetry

    Projeto da CNCF que padroniza como gerar, coletar e exportar telemetria. Instrumente uma vez, envie para qualquer backend.

    APIo código cria métricas, spans e logs
    →
    SDKagrega e processa
    →
    ExportadorPrometheus, OTLP…
    →
    BackendPrometheus, Grafana, Datadog, New Relic…
    • Instrumentação automática: bibliotecas (FastAPI, HTTP, banco) já medidas.
    • Instrumentação manual: métricas de negócio (pedidos, valor, uso de tokens).
    • Convenções semânticas: nomes padronizados, como http.server.request.duration.

    Referências: OpenTelemetry docs · HTTP metrics semconv.

    Lendo as métricas que a aplicação expõe

      terminal

      terminal

    3. Veja os baldes (buckets) do histograma de latência da rota /checkout:

      terminal

    Resultado esperado

    • Atributos viram labels; cada combinação de labels é uma série temporal.
    1.4

    Prometheus e PromQL

    Conceito
    Capítulo 4 · Séries temporais

    Um número por instante, para sempre

    O Prometheus (CNCF, criado na SoundCloud em 2012) busca as métricas de cada alvo em intervalos fixos e guarda séries temporais: nome, labels e valores no tempo.

    Arquitetura

    Aplicaçãoexpõe /metrics
    →
    Prometheusscrape a cada 5 s, guarda o TSDB
    →
    PromQLconsulta e agrega
    →
    Grafanavisualiza
    • Modelo pull: o Prometheus busca; a aplicação não precisa saber para onde mandar.
    • Também aceita push via OTLP e remote write, útil para jobs curtos e para o Collector.
    • Alertas: regras no Prometheus + Alertmanager, ou no Grafana.

    Referências: Prometheus overview.

    Tipos de métrica

    TipoComportamentoExemplo no lab
    CounterSó cresce (zera ao reiniciar)loja_pedidos_total
    GaugeSobe e descehttp_server_active_requests
    HistogramContagens por faixa + soma + totalhttp_server_request_duration_seconds
    SummaryPercentis calculados no clientepouco usado com OpenTelemetry

    PromQL essencial

    promql
    # taxa por segundo de um counter, janela de 1 minuto
rate(http_server_request_duration_seconds_count[1m])
# agregando por rota
sum by (http_route) (rate(http_server_request_duration_seconds_count[1m]))
# percentil 95 a partir do histograma
histogram_quantile(0.95, sum by (le) (rate(http_server_request_duration_seconds_bucket[1m])))
# filtro por regex nos labels
http_server_request_duration_seconds_count{http_response_status_code=~"5.."}
    • Nunca use o valor bruto de um counter: use rate() ou increase().
    • Média esconde a cauda: use percentis.
    • Cuidado com cardinalidade: IDs de usuário ou pedido não são labels.

    Referências: Querying Prometheus.

    Prática
    Exercício 1.3

    Os 4 golden signals em PromQL

    ~30 min

    Escrever, no Prometheus, a consulta de cada golden signal da API da Loja.

    1. Abra o Prometheus (porta 9090). Em Status → Target health, confira o alvo loja-api como UP.

    2. Em Query, rode cada consulta e alterne entre Table e Graph:

      promql
      # 1. LATÊNCIA: p95 geral e por rota
histogram_quantile(0.95, sum by (le) (rate(http_server_request_duration_seconds_bucket[1m])))
histogram_quantile(0.95, sum by (le, http_route) (rate(http_server_request_duration_seconds_bucket[1m])))

# 2. TRÁFEGO: requisições por segundo, por rota
sum by (http_route) (rate(http_server_request_duration_seconds_count[1m]))

# 3. ERROS: fração de respostas 5xx (4xx é erro do cliente)
sum(rate(http_server_request_duration_seconds_count{http_response_status_code=~"5.."}[1m]))
  / sum(rate(http_server_request_duration_seconds_count[1m]))

# 4. SATURAÇÃO: CPU do processo (1 = um núcleo) e requisições em andamento
rate(process_cpu_seconds_total{job="loja-api"}[1m])
sum(http_server_active_requests{job="loja-api"})

# BÔNUS: métrica de negócio, pedidos por minuto
sum by (pagamento) (rate(loja_pedidos_total[1m])) * 60
    Resultado esperado
    • O p95 de /checkout fica perto de 0,6 s; as rotas de produto, abaixo de 0,1 s.
    • O tráfego fica entre 3 e 5 requisições por segundo.
    • A taxa de erros 5xx fica perto de 0,3% (falhas de pagamento simuladas no checkout).
    • A CPU fica bem abaixo de 0,1.
    O que aprendemos com este exercício?
    • Cada golden signal é uma consulta PromQL sobre a mesma métrica HTTP, mais as métricas do processo.
    • Separar por http_route mostra qual rota puxa a média para cima.
    Desafio

    Escreva o SLI de disponibilidade (fração de respostas que não são 5xx) e calcule quanto do error budget de um SLO de 99,5% já foi consumido na última hora.

    Grafana: dashboards dos golden signals

    Conceito
    Capítulo 5 · Do número ao painel

    Um dashboard deve responder uma pergunta em segundos

    Às 3h da manhã, ninguém vai escrever PromQL. O dashboard dos golden signals mostra, de cima para baixo, se o serviço está saudável e onde olhar quando não está.

    Boas práticas de dashboard

    Layout

    • Topo: resumo em números (stat)
    • Abaixo: um bloco por sinal, com tendência
    • Do geral para o detalhe

    Leitura

    • Unidades certas (s, req/s, %)
    • Limiares em verde, laranja e vermelho
    • Legenda com média, máximo e último valor

    Como código

    • JSON versionado no Git
    • Provisionado na subida do Grafana
    • Variáveis (ex.: rota) em vez de painéis duplicados

    O dashboard do lab

    LinhaPainéis

    1.6

    Game day: vendo os sinais reagirem

    Conceito
    Capítulo 6 · Quebrando de propósito

    Um dashboard só prova que funciona quando algo dá errado

    A API tem uma rota /chaos que injeta latência e erros, e uma rota /relatorio que consome CPU. Vamos quebrar cada sinal e ver o dashboard contar a história.

    Roteiro do game day

    RodadaAçãoSinal esperado
    1+1 s de latência em todas as rotasLatência p95 sobe; tráfego cai (os clientes esperam mais)
    230% de errosTaxa de 5xx sobe em todas as rotas
    3Rajada de 150 relatórios pesadosCPU e requisições em andamento disparam; latência sobe junto
    4Volta ao normalTodos os sinais se recuperam
    • Anote o horário de cada rodada: é a sua linha do tempo de incidente.
    • Os sinais se influenciam: saturação causa latência; latência reduz tráfego.
    Prática
    Exercício 1.5

    Game day: latência, erros e saturação

    ~25 min

    Injetar falhas na API e identificar cada uma pelo dashboard dos golden signals.

    1. Deixe o dashboard aberto com atualização a cada 10 s. Rodada 1, latência:

      terminal
      curl -s -X POST "localhost:8000/chaos?latencia=1"; echo

      Espere 1 minuto e observe Latência e Tráfego.

    2. Rodada 2, erros:

      terminal
      curl -s -X POST "localhost:8000/chaos?latencia=0&erro=0.3"; echo

      Observe a taxa de 5xx e o painel de respostas por status.

    3. Rodada 3, saturação: desligue os erros e dispare relatórios pesados em paralelo:

      terminal
      curl -s -X POST "localhost:8000/chaos?latencia=0&erro=0"; echo
for i in $(seq 1 150); do curl -s localhost:8000/relatorio > /dev/null & done; wait

    4. Rodada 4, recuperação: aguarde 2 minutos e confira os quatro números do topo.

    5. Ao terminar a aula, pare a stack:

      terminal
      cd ~/observability/aula-1
docker compose down
    Resultado esperado
    • Rodada 1: p95 acima de 1 s e tráfego menor.
    • Rodada 2: taxa de 5xx perto de 30% e barras de 500 no painel de status.
    • Rodada 3: CPU perto de 1 núcleo, mais de 100 requisições em andamento e p95 de vários segundos.
    • Rodada 4: os sinais voltam aos valores normais.
    O que aprendemos com este exercício?
    • Cada falha tem uma assinatura nos golden signals.
    • Saturação aparece primeiro como fila (requisições em andamento) e depois como latência.
    • Sem os quatro sinais juntos, é fácil confundir causa e efeito.
